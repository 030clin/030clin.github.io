## 프로젝트 소개

Sashimi Six LMS는 자격증 학습과 취업 준비를 하나의 흐름으로 연결하는 LMS 플랫폼이다.

전체 프로젝트는 Module 3, 4, 5에 걸쳐 약 3개월 동안 진행되며,  
Module 3에서는 ERD와 백엔드 공통 구조를 설계하고 AI 기능의 기본 흐름을 구현했다.

Module 4에서는 앞서 만든 구조를 실제 서비스 흐름에 맞게 고도화했다.

나는 Module 4에서 **BE·DBA 및 AI 기능 담당자**로 참여하며 다음 작업을 중심으로 진행했다.

- AI 이력서 평가 기준 구체화
- 채용공고 기반 AI 추천 기능 고도화
- Gemini에서 OpenAI로 모델 전환
- AI 응답 구조화 및 fallback 설계
- 채용공고 URL 검증과 SSRF 방어
- 비동기 추천 처리와 polling 흐름 정리
- AI 전용 Executor와 모니터링 지표 구성
- 자격증 코드·시험 일정·NCS 공공데이터 연계
- 외부 API 장애를 고려한 null-safe 응답 정책 수립
- 프론트엔드와 API 상태 및 응답 계약 정리
- Module 5 개발을 위한 인수인계 문서 작성

Module 4에서 가장 중요하게 생각한 것은 단순히 AI API를 연결하는 일이 아니었다.

**AI 호출 전에는 잘못된 요청을 차단하고, 호출 후에는 불완전한 응답이 그대로 서비스 데이터가 되지 않도록 방어하는 것**이 핵심 목표였다.

---

## Module 4에서 마주한 핵심 문제

Module 3에서는 외부 API 의존성을 줄이기 위해 Stub 응답으로 AI 기능 흐름을 먼저 검증했다.

Stub은 빠르고 일정한 응답을 반환하기 때문에 기능이 즉시 완료되는 것처럼 보였다.  
하지만 실제 OpenAI를 연결하자 다음과 같은 차이가 드러났다.

- AI 분석 시간이 일정하지 않음
- 응답이 누락되거나 형식이 달라질 수 있음
- 일부 필드가 `null` 또는 빈 배열로 반환될 수 있음
- 외부 API 장애와 Rate Limit에 영향을 받음
- 추천 자격증이 실제 내부 데이터와 연결되지 않을 수 있음
- 채용공고 URL에서 본문 추출이 실패할 수 있음
- AI 작업이 몰리면 일반 비동기 작업과 서버 자원을 경쟁할 수 있음
- 프론트엔드가 AI 문장을 해석해 상태를 판단하면 화면 표현이 달라질 수 있음

또한 AI 추천 결과를 서비스 데이터와 연결하려면 다음 공공데이터 흐름도 함께 해결해야 했다.

```text
추천 자격증명
→ 자격증 종목코드 조회
→ jmCd 매핑
→ 시험 일정 조회
→ LMS 내부 강의 매칭
```

AI 응답 하나만 잘 받아오는 것으로는 기능이 완성되지 않았다.

AI, 공공데이터, 내부 DB, 프론트엔드가 하나의 흐름으로 연결되어야 실제 사용 가능한 서비스가 될 수 있었다.

## 1. AI 이력서 평가에서 역할을 분리하다

이력서 평가 기능은 다음 API로 제공했다.

```http
POST /resumes/{resumeId}/ai-review
```

이 기능은 사용자가 결과를 즉시 확인해야 하므로 동기 방식으로 처리했다.

초기에는 AI가 점수와 피드백을 모두 판단하는 방식을 고려했지만, 모델 응답에 따라 동일한 이력서의 점수가 달라질 수 있다는 문제가 있었다.

학력, 경력 수, 근무 기간, 자격증 개수처럼 기준이 명확한 요소까지 AI가 판단하게 하면 평가 결과의 일관성을 보장하기 어렵다.

따라서 역할을 다음처럼 나누었다.

### 백엔드가 담당하는 영역

- 학력 점수 계산
- 경력 개수 계산
- 총 근무 기간 계산
- 자격증 개수 계산
- 최종 평균 점수 산출
- 점수에 따른 평가 등급 결정
- 80점 이상 항목의 강점 문구 생성

### AI가 담당하는 영역

- 경력 업무 연속성 분석
- 보완할 점 작성
- 개선 방향 제안
- 사용자가 이해하기 쉬운 피드백 생성

평가 등급은 백엔드의 고정된 기준으로 관리했다.

```text
0~60   : 보완 필요
61~79  : 보통
80~89  : 양호
90~100 : 우수
```

이를 통해 계산 가능한 영역은 항상 동일한 결과를 제공하고,  
AI는 정성적인 피드백에 집중하도록 역할을 분리했다.

### 이 설계를 통해 얻은 효과

- 동일한 이력서에 대해 일관된 점수 제공
- 모델 변경이 점수 정책에 미치는 영향 최소화
- 평가 기준을 코드와 정책으로 명확하게 관리
- AI 장애 시에도 핵심 점수 계산 가능
- AI를 모든 판단의 주체가 아닌 보조 도구로 활용

**AI가 잘하는 일과 백엔드가 책임져야 하는 일을 구분하는 것이 이 기능의 핵심 설계였다.**

## 2. 이력서 데이터를 구조화된 상태로 관리하다

이력서는 사용자가 하나만 작성하고 계속 수정하는 정책으로 구성했다.

학력, 경력, 자격증은 문자열 한 덩어리로 저장하지 않고 구조화된 리스트로 관리했다.

이 과정에서 프론트엔드와 다음 정책을 명확히 맞출 필요가 있었다.

### 경력 종료일 검증

- 재직 중이면 `endYearMonth`는 반드시 `null`
- 재직 중이 아니면 `endYearMonth`는 필수

### 고용 형태 검증

- `employmentType=OTHER`이면 `customEmploymentType` 필수

### 빈 값 처리

프론트엔드는 빈 문자열이나 `"undefined"`를 보내지 않고 실제 `null`을 전달해야 한다.

### 자격증 취득일 검증

자격증 취득일은 미래 날짜가 될 수 없도록 검증했다.

이처럼 입력 정책을 명확히 하지 않으면 AI 평가보다 먼저 잘못된 이력서 데이터가 DB에 저장될 수 있다.

따라서 AI 기능을 안정화하려면 모델 응답뿐 아니라  
**AI에 전달되기 전 원본 데이터의 품질도 함께 관리해야 했다.**

## 3. 채용공고 추천을 비동기 상태 기반으로 설계하다

채용공고 기반 추천은 외부 URL 본문 추출과 AI 분석을 포함하므로 처리 시간이 길어질 수 있다.

사용하는 API는 다음과 같다.

```http
POST /recommendations/job-posting
GET /recommendations/job-posting/{recommendationId}
```

### POST 요청의 역할

```text
요청값 검증
→ 추천 요청 데이터 저장
→ 상태를 PENDING으로 설정
→ recommendationId 반환
```

### 비동기 분석 서비스의 역할

```text
채용공고 본문 추출
→ 본문 유효성 검증
→ OpenAI 분석
→ 응답 파싱 및 검증
→ 자격증·강의 데이터 보강
→ 결과 저장
→ COMPLETED 또는 FAILED로 상태 변경
```

상태는 다음과 같이 관리했다.

```text
PENDING   : 분석 중
COMPLETED : 분석 완료
FAILED    : 분석 실패
```

프론트엔드는 POST 응답을 받은 뒤 다음 API를 일정 간격으로 호출한다.

```http
GET /recommendations/job-posting/{recommendationId}
```

이를 통해 상태가 `COMPLETED`가 될 때까지 결과를 조회하는 polling 방식을 사용했다.

### 왜 polling이 필요했는가

Stub 환경에서는 응답이 즉시 반환되어 비동기 분석도 바로 끝나는 것처럼 보였다.

하지만 실제 OpenAI 연동에서는 다음 문제로 완료 시점을 예측하기 어려웠다.

- 모델 응답 시간 변동
- 네트워크 지연
- 외부 API Rate Limit
- 동시 요청 수
- 본문 길이에 따른 처리 시간 차이

따라서 POST 직후 한 번만 조회하는 방식으로는 결과 완료를 보장할 수 없었다.

**비동기 기능에서는 결과 데이터뿐 아니라 상태 자체가 API 계약의 일부가 되어야 했다.**

## 4. `@Async` 작업을 별도 서비스로 분리하다

Spring의 `@Async`는 프록시 기반으로 동작한다.

같은 클래스 내부에서 비동기 메서드를 직접 호출하면 프록시를 거치지 않아 비동기로 실행되지 않을 수 있다.

따라서 요청 접수와 실제 분석 책임을 별도 Bean으로 분리했다.

```text
JobPostingRecommendationService
├── 요청 검증
├── PENDING 데이터 저장
├── 중복 요청 확인
└── recommendationId 반환

JobPostingRecommendationAsyncService
├── 채용공고 본문 분석
├── OpenAI 호출
├── 응답 파싱
├── 결과 저장
└── 상태 업데이트
```

이 구조는 단순히 어노테이션을 붙이기 위한 분리가 아니다.

사용자 요청을 빠르게 접수하는 흐름과 오래 걸리는 외부 분석 작업의 책임을 명확하게 분리하기 위한 선택이었다.

### 남아 있는 개선점

트랜잭션이 커밋되기 전에 비동기 작업이 시작되면 Async Service에서 아직 저장되지 않은 데이터를 조회할 가능성이 있다.

향후에는 다음과 같은 구조로 개선할 수 있다.

```text
추천 요청 저장
→ 트랜잭션 커밋
→ 이벤트 발행
→ 이벤트 리스너에서 비동기 분석 시작
```

## 5. AI 전용 Executor를 분리하다

AI 분석은 일반적인 비동기 작업보다 처리 시간이 길고 외부 API 상태의 영향을 크게 받는다.

기본 Executor를 함께 사용하면 AI 요청이 몰렸을 때 다음 문제가 발생할 수 있다.

- 동시에 너무 많은 OpenAI 호출 발생
- 서버 Thread 과다 사용
- 다른 비동기 작업까지 지연
- 대기 작업 수 확인 어려움
- 사용자가 오랫동안 `PENDING` 상태만 확인

따라서 AI 분석 전용 ThreadPool을 분리했다.

```text
사용자 요청
→ AI 전용 Executor
→ 실행 가능하면 즉시 분석
→ 실행 중 작업이 가득 차면 Queue 대기
→ OpenAI 호출
→ 결과 저장
```

전용 Executor를 통해 동시에 처리할 AI 분석 수와 대기 작업 수를 제한할 수 있었다.

### 주요 설정 기준

- Core Pool Size
- Max Pool Size
- Queue Capacity
- AI 전용 Thread Name Prefix
- 작업 거절 정책

AI 기능에서 중요한 것은 무조건 많은 요청을 동시에 실행하는 것이 아니다.

외부 API의 Rate Limit과 서버 자원을 고려해  
**감당 가능한 양만 처리하도록 제어하는 것**이 중요했다.

## 6. AI 응답을 enum으로 구조화하다

채용공고와 이력서를 비교한 적합도 결과는 다음 세 영역으로 나누었다.

- 학력
- 경력
- 자격증

초기에는 AI가 생성한 문장을 프론트엔드가 읽고 상태를 판단하는 방식도 가능했다.

예를 들어 `"충분히 충족합니다"` 또는 `"일부 부족합니다"`와 같은 문장을 프론트에서 분석할 수 있다.

하지만 AI 문장은 매번 달라질 수 있으므로 화면 표시가 불안정해질 수 있다.

따라서 백엔드 응답에 다음 상태값을 포함했다.

```text
SATISFIED
PARTIALLY_SATISFIED
NOT_SATISFIED
UNKNOWN
```

각 상태의 의미는 다음과 같다.

- `SATISFIED`: 조건 충족
- `PARTIALLY_SATISFIED`: 일부 충족
- `NOT_SATISFIED`: 미충족
- `UNKNOWN`: 채용공고 조건이 불분명해 판단 보류

`UNKNOWN`은 이력서가 없다는 의미가 아니다.

채용공고에 학력이나 경력 조건이 명확하게 작성되지 않아 판단하기 어려운 경우를 의미한다.

또한 다음 조건에 따라 프론트 화면을 구분했다.

```text
resumeBased=false 또는 fitAnalysis=null
→ 이력서 기반 적합도 없음
→ 이력서 작성 안내 화면 표시

resumeBased=true 및 fitAnalysis 존재
→ 학력·경력·자격증 적합도 카드 표시
```

이렇게 AI 문장을 상태값으로 구조화하면서  
프론트엔드는 자연어를 추론하지 않고 정해진 상태를 기준으로 화면을 표시할 수 있게 되었다.

## 7. Gemini에서 OpenAI로 전환하다

초기 AI 기능은 Gemini 기반으로 설계했지만, Module 4에서는 OpenAI로 전환했다.

실제 AI 호출 환경과 Stub 검증 환경을 프로필로 분리했다.

```text
local
→ Stub Adapter 사용

local,openai
→ 실제 OpenAI Adapter 사용
```

필요한 환경변수는 다음과 같다.

```text
OPENAI_API_KEY
OPENAI_MODEL=gpt-4o-mini
```

Application Service는 AI Port Interface만 바라보도록 구성했기 때문에, 모델 공급자가 변경되어도 핵심 비즈니스 로직의 수정 범위를 줄일 수 있었다.

```text
Application Service
→ AI Port
→ OpenAI Adapter 또는 Stub Adapter
```

### Stub을 유지한 이유

Stub은 실제 기능을 대신하는 임시 코드만을 의미하지 않는다.

다음 환경에서는 의도적으로 Stub이 필요했다.

- API Key 없이 로컬 기능 흐름 검증
- AI 호출 비용 없이 반복 테스트
- 일정한 응답을 사용한 단위 테스트
- 외부 API 장애와 무관한 서비스 테스트
- 부하테스트에서 OpenAI 비용 및 Rate Limit 분리

실제 시연과 운영 검증은 OpenAI 프로필을 사용하고,  
개발과 반복 테스트는 Stub으로 진행하도록 역할을 분리했다.

## 8. 프롬프트에 전달하는 값을 사람이 이해할 수 있게 변환하다

DB와 Java 코드에서는 enum이 일관된 상태 관리에 유리하다.

하지만 enum 값을 그대로 AI 프롬프트에 전달하면 모델이 의미를 정확히 해석하지 못하거나 불필요한 추론을 할 수 있다.

예를 들어 다음 값을 그대로 전달하지 않도록 변환했다.

```text
BACHELOR
→ 학사

EXPECTED_GRADUATION
→ 졸업 예정

FULL_TIME
→ 정규직
```

또한 다음 정책을 프롬프트에 반영했다.

- 졸업 예정은 학력 조건 충족으로 판단
- 채용공고에 없는 조건은 임의로 추론하지 않음
- 사용자 이력서 요약을 실제 프롬프트에 포함
- 명확하지 않은 조건은 `UNKNOWN`으로 반환
- 지정된 JSON 구조 외의 문장을 반환하지 않도록 요청

프롬프트는 단순 질문 문장이 아니라  
**AI가 지켜야 할 비즈니스 정책을 전달하는 계약**으로 관리했다.

---

## 9. AI 응답을 그대로 신뢰하지 않고 검증하다

LLM은 요청한 형식을 항상 정확하게 반환하지 않는다.

다음과 같은 문제가 발생할 수 있다.

- JSON 앞뒤에 설명 문장 포함
- 필수 필드 누락
- enum에 없는 상태값 반환
- 배열 대신 문자열 반환
- 내부 DB에 존재하지 않는 자격증이나 강의 반환
- `null`과 빈 배열을 일관되지 않게 사용

따라서 AI 응답을 그대로 저장하지 않고 다음 단계를 거쳤다.

```text
OpenAI 응답 수신
→ JSON 추출
→ JSON 파싱
→ 필수 필드 검증
→ enum 값 검증
→ 내부 데이터와 매칭
→ 누락 값 fallback
→ 최종 결과 저장
```

핵심 원칙은 다음과 같았다.

> 외부 AI 응답은 참고할 수 있는 데이터이지, 검증 없이 신뢰할 수 있는 서비스 데이터가 아니다.

---

## 10. 자격증 추천에 fallback을 적용하다

AI가 추천 자격증 배열을 비워서 반환하는 경우가 있었다.

하지만 적합도 분석에는 사용자가 보유하지 않은 자격증이 `missingItems`로 포함될 수 있었다.

따라서 AI가 추천 자격증을 반환하지 않아도 다음 데이터를 활용해 fallback 추천을 생성했다.

```text
fitAnalysis.certification.missingItems
→ 자격증명 추출
→ 사용자가 이미 보유한 자격증 제외
→ 자격증 코드 조회
→ 시험 일정 보강
→ 추천 자격증 응답 생성
```

이를 통해 AI 응답 일부가 비어 있어도 전체 추천 기능이 사라지지 않도록 했다.

### 추천 제외 정책

사용자가 이미 보유한 자격증은 추천 결과에서 제외했다.

AI가 보유 여부를 잘못 판단할 수 있으므로, 최종 제외 처리는 백엔드가 저장된 이력서 데이터를 기준으로 수행했다.

---

## 11. 자격증 코드와 시험 일정 공공데이터를 연결하다

추천 자격증에 시험 일정을 표시하려면 자격증명만으로는 부족했다.

시험 일정 API 호출에 필요한 `jmCd`를 먼저 확보해야 했다.

전체 흐름은 다음과 같다.

```text
AI 또는 fallback이 추천 자격증명 생성
→ qualification_codes에서 자격증명 조회
→ jmCd 확보
→ 시험 일정 API 호출
→ 접수 시작일·종료일·시험일 보강
→ 응답 반환
```

프론트 확인 과정에서는 다음 필드가 `null`로 내려가는 문제가 있었다.

- `certificateId`
- `applicationStartDate`
- `applicationEndDate`
- `nextExamDate`

이 문제는 다음 순서로 확인했다.

1. 자격증명과 내부 코드 데이터 매핑
2. 자격증 코드에서 `jmCd` 조회
3. `jmCd`를 사용한 시험 일정 API 호출
4. 해당 연도에 일정이 실제로 존재하는지 확인
5. 최종 응답 DTO 매핑 확인

`certificateId`가 정상적으로 연결되지 않으면 이후 시험 일정 조회도 실패할 가능성이 높기 때문에 가장 먼저 확인해야 했다.

---

## 12. 외부 API 중단에 대비한 seed 데이터와 null-safe 정책

개발 중 Q-Net 자격증 종목코드 API가 일시 중단되는 상황이 발생했다.

외부 API가 복구될 때까지 전체 기능을 멈출 수 없었기 때문에 주요 자격증에 대해 임시 seed 데이터를 사용했다.

```text
정보처리기사       : 1320
정보처리산업기사   : 2290
정보보안기사       : 1325
빅데이터분석기사   : 1324
사무자동화산업기사 : 2193
```

시험 일정 API는 사용할 수 있었지만, 특정 자격증은 해당 연도 일정이 없어서 `syncedCount: 0`이 될 수 있었다.

이 경우 잘못된 날짜를 만들어내지 않고 다음 값들을 `null`로 반환하도록 했다.

```text
applicationStartDate: null
applicationEndDate: null
nextExamDate: null
```

외부 데이터가 없다는 이유로 추천 결과 전체를 실패시키지 않고,  
제공 가능한 정보만 반환하는 방식을 선택했다.

---

## 13. NCS 데이터를 실시간 호출하지 않고 미리 동기화하다

NCS는 강의 상세 페이지에서 활용하는 직무 분류 데이터다.

강의 상세 조회 때마다 외부 NCS API를 호출하면 다음 문제가 발생할 수 있다.

- 외부 API 응답 지연
- 호출 한도 초과
- 외부 서비스 장애가 강의 상세 장애로 전파
- 동일 데이터 반복 호출
- 화면 응답시간 증가

따라서 관리자 동기화 API를 통해 NCS 데이터를 미리 DB에 저장했다.

```http
POST /admin/ncs/sync?dutyCd={직무코드}
```

처리 흐름은 다음과 같다.

```text
관리자가 동기화 요청
→ 공공데이터 NCS API 호출
→ ncs_info 테이블 저장
→ 카테고리와 NCS 반자동 매핑
→ 강의 상세 조회 시 DB 데이터 반환
```

강의 상세에서는 다음 API를 사용한다.

```http
GET /api/courses/{courseId}
```

NCS 정보가 없더라도 강의 상세 전체를 `404 Not Found`로 처리하지 않았다.

```json
{
  "ncs": null
}
```

프론트에서는 `null`인 경우 `-` 또는 정보 없음으로 표시할 수 있도록 계약을 맞췄다.

### NCS 표현 방식

NCS는 자격증 그 자체가 아니라 직무 분류 체계다.

따라서 다음처럼 표현하지 않는다.

```text
정보처리기사 = 응용SW엔지니어링
```

대신 다음과 같이 설명한다.

```text
정보처리기사의 NCS 연계 직무를 응용SW엔지니어링으로 매핑
```

---

## 14. 사이트 카테고리와 NCS 직무를 반자동 매핑하다

사이트의 자격증 카테고리와 NCS 직무 코드를 연결하기 위해 반자동 매핑 규칙을 사용했다.

예시는 다음과 같다.

```text
정보처리기사
→ 응용SW엔지니어링
→ 20010202

정보보안기사
→ 보안엔지니어링
→ 20010206

네트워크관리사
→ NW엔지니어링
→ 20010205

SQLD
→ DB엔지니어링
→ 20010204

ADsP / 빅데이터분석기사
→ 빅데이터분석
→ 20010105
```

관리자가 `/admin/ncs/sync`를 호출하면 다음 두 작업을 수행한다.

1. NCS 데이터를 `ncs_info`에 저장
2. 매핑 규칙에 해당하는 카테고리의 `ncs_info_id` 연결

코드에 해당 카테고리 매핑이 없다면 NCS 정보만 저장되고 카테고리 연결은 수행되지 않을 수 있다.

매핑 코드를 추가한 경우에는 반드시 다음 과정이 필요하다.

```text
매핑 코드 수정
→ 서버 재배포
→ 관리자 sync API 재호출
→ 강의 상세 응답 확인
```

---

## 15. 강의 추천은 AI가 아닌 백엔드가 내부 데이터와 매칭하다

AI가 임의로 강의명을 생성하게 하면 LMS에 실제로 존재하지 않는 강의를 추천할 수 있다.

따라서 AI는 필요한 자격증과 역량을 분석하고, 실제 강의 추천은 백엔드가 내부 강의 데이터와 연결하도록 했다.

```text
AI 분석 결과
→ 추천 자격증 또는 부족 역량 추출
→ LMS 내부 강의 검색
→ 카테고리·자격증명·기술 키워드 매칭
→ CourseRecommendationResponse 생성
```

이 과정에서 다음 문제가 확인되었다.

- 추천 강의의 `instructor`가 `null`
- `matchedSkill`이 DB 세부 카테고리명과 불일치

`CourseRecommendationResponse`가 `course.instructor()` 값을 그대로 내려주는 구조라면, 응답 DTO보다 이전 단계에서 `CourseRecommendation`을 생성할 때 강사명을 넣지 않았을 가능성이 크다.

따라서 문제를 다음 순서로 추적해야 했다.

```text
Course Entity 또는 조회 결과
→ 내부 Course 모델 변환
→ CourseRecommendation 생성
→ CourseRecommendationResponse 변환
```

`matchedSkill`도 내부 분석 키워드보다 프론트에서 실제 표시하는 DB 세부 카테고리명과 맞추는 것이 일관된 화면을 만드는 데 적합했다.

---

## 16. 채용공고 URL 입력에서 SSRF를 방어하다

사용자가 URL을 입력하면 서버가 해당 주소로 직접 요청을 보내 채용공고 본문을 추출한다.

이 기능은 서버가 사용자가 지정한 주소로 요청한다는 점에서 SSRF 위험이 있다.

예를 들어 악의적인 사용자가 다음 주소를 입력할 수 있다.

```text
http://localhost
http://127.0.0.1
http://169.254.169.254
사설 네트워크 IP
```

이를 방지하기 위해 URL 검증 정책을 적용했다.

### 허용

```text
http
https
```

### 차단

- localhost
- loopback 주소
- link-local 주소
- private network
- 허용하지 않은 프로토콜

Jsoup 요청에도 다음 제한을 적용했다.

- 연결 timeout
- 읽기 timeout
- redirect 횟수 제한
- 본문 최소 길이 검증
- 빈 페이지 및 로그인 페이지 차단

본문 추출에 성공하더라도 내용이 지나치게 짧다면 AI에 전달하지 않았다.

이를 통해 불필요한 AI 호출 비용을 줄이고, 서버 내부 네트워크 접근 가능성을 차단했다.

---

## 17. 중복 요청을 AI 호출 전에 차단하다

동일한 사용자가 같은 채용공고 URL을 반복해서 요청하면 같은 내용으로 AI API가 여러 번 호출될 수 있다.

이는 다음 문제로 이어질 수 있다.

- OpenAI 호출 비용 증가
- 같은 분석 결과 중복 저장
- 비동기 Queue 불필요하게 증가
- 사용자가 여러 개의 PENDING 결과를 확인해야 함

따라서 AI 호출 전 다음 내용을 확인했다.

- 동일 사용자의 동일 URL 요청 여부
- 이미 완료된 결과 재사용 가능 여부
- 현재 분석 중인 요청 존재 여부
- 본문 추출 결과의 유효성

**AI 호출 자체를 빠르게 만드는 것보다 호출할 필요가 없는 요청을 제거하는 것이 먼저였다.**

---

## 18. 프론트엔드와 null·상태 처리 기준을 맞추다

비동기 추천의 `PENDING` 상태에서는 분석 결과가 아직 존재하지 않는다.

따라서 다음 필드가 `null`일 수 있다.

- `summary`
- `fitAnalysis`
- 추천 자격증
- 추천 강의

프론트엔드가 이를 오류로 판단하지 않도록 상태별 응답 계약을 맞췄다.

### PENDING

```text
분석 중 UI 표시
결과 필드는 null 또는 빈 배열 가능
polling 계속 수행
```

### COMPLETED

```text
분석 결과 화면 표시
fitAnalysis 조건에 따라 적합도 카드 표시
```

### FAILED

```text
실패 안내
재시도 가능 UI 표시
```

또한 종합 코멘트는 AI가 반환한 배열 순서에 의존하지 않고, 프론트에서 다음 순서로 고정 표시하도록 정리했다.

```text
학력
→ 경력
→ 자격증
```

AI 응답의 순서가 바뀌더라도 사용자 화면은 항상 동일하게 유지하기 위한 정책이었다.

---

## 19. AI 기능에 접근 제한을 적용하다

AI 기능은 외부 API 비용이 발생하는 기능이기 때문에 모든 사용자가 제한 없이 호출할 수 없도록 했다.

이력서 평가에서는 다음 조건을 확인했다.

- 로그인 사용자 여부
- 본인 이력서 여부
- 활성 구독 여부
- AI 활용 동의 여부

채용공고 추천 결과도 `userId`를 기준으로 본인 데이터만 조회할 수 있도록 했다.

이러한 접근 제한은 단순 권한 제어뿐 아니라  
AI 비용 관리와 개인정보 보호를 함께 고려한 정책이었다.

---

## 20. AI 비동기 작업을 모니터링하다

비동기 처리를 적용하면 사용자는 빠르게 응답을 받지만, 서버 내부에서 작업이 정상적으로 수행되는지는 별도로 확인해야 한다.

Prometheus와 Grafana를 사용해 AI 관련 지표를 확인할 수 있도록 했다.

### 주요 지표

- AI 요청 수
- AI 성공 수
- AI 실패 수
- AI 접근 제한 차단 수
- 현재 실행 중인 비동기 작업 수
- 비동기 Queue 크기
- 완료된 AI 작업 수
- HTTP 응답시간 P95
- HTTP 응답시간 P99
- AI 실패 로그

특히 Queue 크기가 지속적으로 증가한다면 다음 문제를 의심할 수 있다.

- Executor 처리량 부족
- OpenAI 응답 지연
- 외부 API Rate Limit
- 너무 많은 중복 요청
- 실패 후 재시도 정책 오류

비동기 기능에서는 API 응답시간만 보는 것이 아니라  
**백그라운드 작업의 실행 상태와 대기열을 함께 확인해야 했다.**

---

## 21. Stub과 실제 OpenAI 부하테스트를 분리하다

채용공고 추천은 다음 흐름으로 k6 테스트를 구성할 수 있다.

```text
POST 추천 생성
→ recommendationId 확보
→ GET polling
→ COMPLETED 또는 FAILED 확인
```

하지만 실제 OpenAI를 사용해 많은 가상 사용자를 동시에 테스트하면 다음 문제가 발생한다.

- 테스트 비용 증가
- Rate Limit 도달
- 외부 모델 응답시간이 전체 결과에 크게 영향
- 우리 서버 성능과 외부 API 성능을 구분하기 어려움

따라서 부하테스트를 두 종류로 분리하는 것이 적절했다.

### Stub 기반 테스트

목적:

- 우리 서버의 API 처리량 확인
- Executor와 Queue 동작 확인
- DB 저장 및 polling 구조 검증
- 동시 사용자 수 증가에 따른 응답시간 측정

### 실제 OpenAI 기반 테스트

목적:

- 외부 API 포함 전체 흐름 검증
- 소규모 사용자의 실제 응답시간 확인
- Rate Limit과 실패 처리 확인
- 응답 파싱 안정성 확인

이를 통해 내부 서버 병목과 외부 AI 지연을 구분할 수 있었다.

## Module 4에서 기여한 결과

Module 4에서의 작업은 AI 기능을 추가하는 데 그치지 않았다.

외부 AI와 공공데이터를 실제 서비스에 연결하기 위해 다음과 같은 기준을 마련했다.

- 계산 가능한 평가는 백엔드가 담당
- AI는 정성적 피드백에 집중
- 비동기 추천은 상태 기반 API로 제공
- 프론트엔드는 polling으로 완료 시점을 확인
- AI 문장을 enum 상태값으로 구조화
- 외부 AI 응답은 파싱·검증·보정 후 사용
- AI 응답 누락 시 fallback 적용
- 추천 자격증은 내부 코드와 시험 일정으로 보강
- 강의 추천은 실제 LMS 데이터와 백엔드에서 매칭
- 외부 API 중단 시 seed 데이터와 null-safe 응답 사용
- NCS는 관리자 동기화 후 DB 조회 방식으로 제공
- URL 입력은 SSRF 검증 적용
- AI 작업은 전용 Executor와 운영 지표로 관리
- Stub과 실제 OpenAI 테스트 목적을 분리
- 프론트엔드와 PENDING·null·빈 배열 처리 기준 공유

Module 3에서 설계한 Port-Adapter와 비동기 구조를 기반으로,  
Module 4에서는 실제 외부 API 환경에서 발생하는 실패와 변동성을 서비스가 감당할 수 있도록 고도화했다.

## 아쉬웠던 점과 향후 개선 방향

### polling 부하 개선

현재는 프론트엔드가 일정 주기로 GET 요청을 보내 결과를 확인한다.

향후에는 Server-Sent Events 또는 WebSocket을 사용해 완료 시점을 서버에서 전달하는 방식도 검토할 수 있다.

### 트랜잭션 이후 비동기 실행 보장

`@TransactionalEventListener` 또는 메시지 큐를 사용해 DB 커밋 이후 분석이 시작되도록 개선할 수 있다.

### AI 평가 체계 고도화

프롬프트 버전, 모델 버전, 응답 품질 평가 결과를 함께 저장해 모델 변경에 따른 품질 차이를 추적할 수 있다.

### 공공데이터 동기화 자동화

관리자 수동 호출 외에도 스케줄러를 사용해 자격증 코드와 시험 일정을 주기적으로 갱신할 수 있다.

### 추천 매칭 정확도 개선

자격증명과 단순 키워드뿐 아니라 NCS 직무, 강의 카테고리, 기술 스택을 함께 사용해 강의 매칭 점수를 계산할 수 있다.

### 실패 복구 정책 구체화

OpenAI 호출 실패와 공공데이터 호출 실패를 구분하고, 재시도 가능한 오류와 즉시 실패해야 하는 오류를 분리할 필요가 있다.

## 배운 점

Module 4를 통해 AI 기능의 핵심은 모델을 호출하는 코드가 아니라는 것을 배웠다.

실제 서비스에 AI를 적용하려면 다음 질문에 답할 수 있어야 했다.

- 잘못된 요청을 AI 호출 전에 어떻게 막을 것인가
- AI 응답이 비어 있으면 무엇으로 대체할 것인가
- 응답 형식이 다르면 어떻게 검증할 것인가
- 내부 DB에 없는 추천 결과를 어떻게 처리할 것인가
- 외부 API가 중단되면 서비스 전체를 실패시킬 것인가
- 오래 걸리는 분석을 사용자 요청과 어떻게 분리할 것인가
- 백그라운드 작업이 밀리는 상황을 어떻게 발견할 것인가
- 프론트엔드가 결과 상태를 어떻게 안정적으로 판단할 것인가
- 비용이 발생하는 기능을 어떤 사용자에게 허용할 것인가
- 테스트에서 외부 의존성을 어떻게 제거할 것인가

특히 AI와 공공데이터를 함께 연동하면서  
외부 응답을 그대로 사용하는 것이 아니라 **내부 서비스 정책에 맞게 검증하고 재구성하는 과정**이 중요하다는 것을 체감했다.
