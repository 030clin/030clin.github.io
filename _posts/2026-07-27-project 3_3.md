## 프로젝트 소개

Sashimi Six LMS는 자격증 학습과 취업 준비를 연결하는 LMS 플랫폼이다.

전체 프로젝트는 Module 3, 4, 5에 걸쳐 약 3개월 동안 진행되었다.

Module 3에서는 전체 ERD와 백엔드 구조를 설계하고, AI 기능을 포함한 주요 도메인의 기반을 만들었다.

Module 4에서는 AI 이력서 평가와 채용공고 추천을 실제 서비스 흐름에 연결하며, 비동기 처리와 외부 데이터 연계, AI 응답 검증 구조를 고도화했다.

마지막 Module 5에서는 기존 AI 기능을 단순히 **“호출해서 결과를 보여주는 기능”**으로 두지 않고,

**요청 → 처리 → 저장 → 조회 → 실패 관리 → 사용량 제한까지 포함하는 운영 가능한 서비스 구조**로 확장하는 데 집중했다.

내가 Module 5에서 맡은 주요 역할은 다음과 같다.

- AI 이력서 평가 리팩토링
- 자기소개서 AI 첨삭 기능 구현
- AI 분석 기능의 Spring / FastAPI 역할 분리
- AI 요청 이력 및 최신 결과 조회 구조 설계
- 사용자별 AI 사용량 제한 정책 설계
- AI 결과 보관 정책 설계
- 채용공고 비동기 분석 트랜잭션 문제 개선
- 채용공고 URL 검증 및 SSRF 대응
- DB 기반 추천 강의 매칭 구조 정리
- 개발 DB / 운영 DB 분리 및 Flyway 운영 방식 정리
- AI 장애 및 로그 기반 문제 추적

Module 5에서 가장 중요하게 생각한 것은  
**AI 기능을 “동작하는 기능”에서 “운영하고 관리할 수 있는 기능”으로 바꾸는 것**이었다.

---

## Module 5에서 마주한 핵심 문제

AI 기능은 일반적인 CRUD 기능과 다른 특성을 가지고 있었다.

```text
- 외부 AI API 호출 비용이 발생한다.
- 응답 시간이 일정하지 않다.
- 응답 형식이 항상 동일하지 않다.
- Timeout, Quota, Billing 등의 외부 오류가 발생할 수 있다.
- 분석 시간이 긴 기능은 비동기 처리가 필요하다.
- 사용자는 과거 분석 결과를 다시 확인하고 싶어 한다.
- 실패한 요청을 추적할 수 있어야 한다.
- AI 호출이 반복되면 비용과 서버 자원이 함께 증가한다.
````

Module 5에서는 자기소개서 첨삭 기능까지 추가되면서 AI 기능이 여러 도메인으로 확대되었다.

따라서 단순한 모델 호출보다 다음 질문이 중요해졌다.

1. 누가 AI 기능을 사용할 수 있는가?
2. 한 사용자가 얼마나 자주 요청할 수 있는가?
3. 요청 결과를 언제까지 보관할 것인가?
4. 실패한 AI 요청은 어떻게 추적할 것인가?
5. 오래 걸리는 분석은 어떻게 처리할 것인가?
6. Spring과 FastAPI는 각각 어떤 책임을 가져야 하는가?
7. 개발 중 DB 변경을 운영 환경에 어떻게 안전하게 반영할 것인가?

## 1. Spring과 FastAPI의 책임을 분리하다

AI 기능이 증가하면서 Spring 내부에서 인증, 데이터 처리, 프롬프트 생성, AI 호출, 응답 파싱까지 모두 담당하는 구조는 유지보수하기 어려워질 수 있었다.

Module 5에서는 AI 처리 영역을 FastAPI로 분리하고, Spring과 책임을 나누었다.

### Spring

```text
- 인증 / 인가
- 사용자 데이터 조회
- 요청 유효성 검증
- AI 요청 이력 저장
- 사용량 제한
- AI 결과 저장 및 조회
- 트랜잭션 관리
- 서비스 정책 관리
```

### FastAPI

```text
- Prompt Builder
- AI API 호출
- 텍스트 전처리
- AI 응답 JSON 파싱
- Pydantic 기반 응답 Validation
```

전체 흐름은 다음과 같이 구성했다.

```text
Client
→ Spring Boot
→ 사용자 / 권한 / 사용량 검증
→ FastAPI
→ Prompt 생성
→ AI 분석
→ 응답 검증
→ Spring
→ 결과 저장
→ Client 응답
```

이 구조를 선택한 이유는 AI 영역의 변경 주기가 일반적인 서비스 로직보다 빠르기 때문이다.

모델, 프롬프트, 응답 스키마가 변경되더라도 Spring의 핵심 도메인 로직에 미치는 영향을 줄이고자 했다.

## 2. 프롬프트와 코드를 분리하다

자기소개서와 채용공고 분석 프롬프트는 점점 길어졌고, 단순한 문자열을 넘어 하나의 운영 규칙처럼 사용되기 시작했다.

이를 코드 안에 직접 작성하면 다음 문제가 생길 수 있었다.

* 비즈니스 코드와 프롬프트 규칙이 섞임
* 프롬프트 수정 시 코드 가독성이 떨어짐
* 긴 규칙을 검토하기 어려움
* 향후 프롬프트 버전 관리가 어려움

그래서 규정 파일을 코드에서 분리했다.

```text
prompt_templates/
└── job_posting_analysis_regulation.txt

prompts/
└── cover_letter_review_regulation.txt
```

FastAPI는 해당 파일을 불러온 뒤 사용자 입력값만 필요한 위치에 삽입해 최종 Prompt를 생성하도록 구성했다.

프롬프트를 별도 파일로 관리하면서 **AI Prompt도 하나의 운영 정책 자산**으로 관리할 수 있는 기반을 만들었다.

## 3. AI 요청을 이력으로 관리하다

AI 기능을 처음 구현했을 때는 사용자가 요청하면 결과를 계산해 바로 반환하는 형태가 중심이었다.

하지만 서비스 기능으로 확장하면서 다음 요구사항이 생겼다.

* 페이지를 나갔다가 돌아와도 최근 결과를 확인하고 싶음
* 실패한 AI 요청을 추적해야 함
* 기능별 사용량을 확인해야 함
* 비동기 요청의 현재 상태를 관리해야 함

이를 위해 AI 요청 이력 구조를 도입했다.

```text
ai_request_histories

- userId
- featureType
- status
- requestSnapshotJson
- resultJson
- errorMessage
- createdAt
- completedAt
```

상태는 다음과 같이 관리했다.

```text
PENDING
COMPLETED
FAILED
```

이를 통해 단순히 결과만 저장하는 것이 아니라,

**누가 어떤 AI 기능을 요청했고, 성공했는지 실패했는지까지 추적할 수 있는 구조**를 만들었다.

## 4. AI 사용량 제한 정책을 설계하다

AI 기능은 요청할 때마다 외부 API 비용이 발생한다.

따라서 일반 API처럼 무제한 호출을 허용하면 짧은 시간 동안 반복 요청이 발생했을 때 비용과 Rate Limit 문제가 생길 수 있다.

Module 5에서는 사용자별 AI 요청 횟수를 제한했다.

```text
이력서 AI 평가      : 1시간 10회
자기소개서 AI 첨삭   : 1시간 10회
채용공고 AI 분석     : 1시간 10회

전체 AI 기능 합산    : 1시간 30회
```

1시간 단위로 제한한 이유는 정상적인 수정·재분석 흐름까지 지나치게 막지 않으면서, 짧은 시간의 반복 호출만 제어하기 위해서였다.

또한 조회 요청은 제한 대상에서 제외했다.

```text
제한 대상
→ POST 기반 AI 분석 요청

제한 제외
→ GET 최신 결과 조회
→ GET 상세 결과 조회
```

이미 생성된 데이터를 조회하는 API는 외부 AI 호출 비용이 발생하지 않기 때문이다.

이 작업을 통해 AI 기능의 사용 정책 역시 백엔드가 관리해야 하는 비즈니스 규칙이라는 점을 경험했다.

## 5. 이력서 AI 평가에서 계산과 AI의 역할을 분리하다

이력서 평가는 학력, 경력, 자격증을 기준으로 점수와 피드백을 제공하는 기능이다.

AI가 모든 평가를 담당하면 같은 이력서라도 모델 응답에 따라 결과가 달라질 수 있다는 문제가 있었다.

그래서 계산 가능한 영역은 백엔드가 담당하도록 리팩토링했다.

```text
학력
경력 수
총 근무 기간
자격증 개수
평균 점수
평가 등급

→ Backend Calculator
```

반대로 AI는 다음과 같은 정성 영역에 집중했다.

```text
경력 보완점
업무 경험의 연속성
자연어 피드백
개선 방향
```

구조를 단순화하면 다음과 같다.

```text
명확한 기준
→ Backend

해석이 필요한 영역
→ AI
```

또한 외부 AI 호출에 실패하더라도 핵심 평가가 모두 사라지지 않도록 기본 피드백 fallback을 제공했다.

이 구조를 통해 **AI의 변동성이 서비스의 평가 기준까지 흔들지 않도록 역할을 분리**할 수 있었다.

## 6. 자기소개서 AI 첨삭 기능을 구현하다

Module 5에서 새롭게 구현한 핵심 기능 중 하나는 자기소개서 AI 첨삭이다.

자기소개서는 총 5개의 문항으로 구성했다.

```text
1. 자기 소개
2. 성격의 장점과 단점
3. 대표 프로젝트 경험
4. 문제 해결 경험
5. 상사와 의견이 다를 경우
```

자기소개서 AI 기능은 단순히 수정된 문장 하나를 반환하는 방식보다,

사용자가 자신의 글에서 무엇을 보완해야 하는지 확인할 수 있도록 분석 결과를 구조화하는 데 초점을 맞췄다.

### 작성 페이지

```text
- 작성 완료 문항 수
- 수정 필요 문항 수
- 보완 권장 문항 수
- 맞춤법 / 오타 수정 수
- 반복 표현 수
- 평균 문장 길이
- AI 종합 코멘트
```

### 상세 결과 페이지

```text
- 문항별 상태
- 맞춤법 수정 내용
- 반복 표현
- 종합 피드백
- 개선 예시
```

Spring은 자기소개서 데이터와 결과 저장·조회를 담당하고, FastAPI는 AI 분석과 응답 검증을 담당하도록 역할을 분리했다.

## 7. 채용공고 분석을 비동기 상태 기반으로 처리하다

채용공고 분석은 URL 또는 텍스트를 입력받아 다음 결과를 제공하는 기능이다.

```text
- 채용공고 핵심 요약
- 사용자 이력서 적합도
- 부족한 역량
- 추천 자격증
- 추천 강의
```

외부 AI 분석에는 시간이 필요하므로 요청과 실제 분석을 분리했다.

```text
사용자 요청
→ Recommendation PENDING 저장
→ recommendationId 반환
→ 비동기 AI 분석
→ 결과 저장
→ COMPLETED 또는 FAILED
→ Frontend polling
```

이 방식으로 사용자는 AI 분석이 끝날 때까지 HTTP 요청을 계속 유지하지 않아도 된다.

## 8. 비동기 처리에서 트랜잭션 commit 문제를 해결하다

비동기 채용공고 분석 과정에서 중요한 문제가 발생했다.

다음 순서로 코드를 작성했다고 해서 실제 DB 반영도 같은 순서로 끝나는 것은 아니었다.

```text
Recommendation 저장
→ Async 분석 실행
```

Spring의 트랜잭션 안에서는 `save()`가 호출되어도 실제 commit이 메서드 종료 이후에 이루어질 수 있다.

그 사이 비동기 Thread가 먼저 실행되면 아직 commit되지 않은 데이터를 조회하려 할 수 있었다.

이를 해결하기 위해 실제 비동기 분석 시작 시점을 **트랜잭션 commit 이후**로 변경했다.

```java
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            asyncService.analyze(
                recommendationId,
                userId,
                historyId
            );
        }
    }
);
```

전체 흐름은 다음과 같이 바뀌었다.

```text
PENDING 데이터 저장
→ Transaction Commit
→ afterCommit()
→ Async 분석 시작
→ OpenAI / Gemini 호출
→ 결과 저장
```

이 경험을 통해 비동기 처리에서 중요한 것은 단순한 코드 실행 순서가 아니라,

**데이터가 실제로 다른 트랜잭션에서 조회 가능한 시점**이라는 것을 배웠다.

## 9. 채용공고 URL 입력의 SSRF 위험을 방어하다

채용공고 URL 분석 기능은 사용자가 입력한 주소로 백엔드 서버가 직접 요청을 보내기 때문에 SSRF 위험이 존재한다.

예를 들어 다음과 같은 주소가 입력될 수 있다.

```text
http://localhost
http://127.0.0.1
사설 IP
link-local IP
metadata 서버 주소
```

따라서 URL 요청 전에 검증 단계를 추가했다.

### 허용

```text
http
https
```

### 차단

```text
localhost
loopback
private network
link-local
metadata IP
```

또한 다음과 같은 방어 정책도 적용했다.

```text
- scheme 없는 URL은 https 기준으로 보정
- redirect 이후 최종 URL 재검증
- Jsoup timeout 적용
- 지나치게 짧은 본문 차단
```

일부 사이트는 크롤링 구조상 본문 추출이 어려울 수 있었다.

이 경우 보안 정책을 우회하기보다 **텍스트 직접 입력이라는 대체 경로를 제공하는 방식**을 선택했다.

## 10. 추천 강의는 AI가 만들지 않도록 했다

채용공고 분석 결과에는 사용자에게 필요한 강의 추천도 포함된다.

하지만 AI가 강의명을 직접 생성하게 하면 실제 LMS에 존재하지 않는 강의를 만들어낼 가능성이 있다.

따라서 AI는 강의명 자체가 아닌 검색 기준만 생성하도록 했다.

```text
AI
→ courseSearchCriteria 생성

Spring
→ DB 조회

LMS DB
→ 승인된 실제 강의만 반환
```

즉,

```text
AI가 “무엇을 찾을지” 결정
Backend가 “실제로 존재하는 데이터”를 찾음
```

의 역할로 분리했다.

이를 통해 생성형 AI의 자유도를 활용하면서도 사용자에게는 검증된 내부 데이터만 제공할 수 있었다.

## 11. AI 결과 저장과 보관 정책을 정리하다

AI 결과를 계속 저장하면 시간이 지날수록 DB 용량이 증가한다.

반대로 모든 결과를 즉시 삭제하면 사용자가 최근 분석 결과를 다시 확인하기 어렵다.

Module 5에서는 AI 결과를 일정 기간 보관하는 정책을 설계했다.

```text
AI 결과 보관 기간
→ 7일
```

즉, AI 결과 저장 자체도 단순 영속화 문제가 아니라,

```text
사용자 편의성
vs
DB 저장 비용
```

사이의 운영 정책으로 바라보았다.

## 12. 개발 DB와 운영 DB를 분리하다

Module 5에서는 AI 요청 이력, 자기소개서 평가 결과 등 새로운 데이터 구조가 추가되면서 DB migration도 빈번하게 발생했다.

개발 중 migration을 운영·시연 DB에 자동 적용하면 기존 데이터를 훼손할 위험이 있었다.

그래서 DB를 목적에 따라 분리했다.

### 개발 DB

```text
sixsashimi_dev

- local profile
- 개발 / 테스트 전용
- Flyway 자동 실행
- migration 검증
- dummy 데이터 허용
```

### 운영·시연 DB

```text
sixsashimi_db

- prod profile
- 기존 데이터 유지
- Flyway 자동 실행 비활성화
- 검증된 SQL만 수동 적용
```

전체 흐름은 다음과 같았다.

```text
Migration 작성
→ DEV DB 자동 반영
→ 팀 테스트
→ DBA 검토
→ PROD SQL 수동 반영
```

이를 통해 DB 변경 테스트와 운영 데이터 보호를 분리할 수 있었다.

## 13. 운영 과정에서 실제 장애를 추적하다

Module 5에서는 구현뿐 아니라 배포 이후 실제 AI 호출을 테스트하면서 여러 문제가 발생했다.

### Gemini quota / billing 오류

```text
AI API
→ 429 응답
→ FAILED 상태 기록
→ errorMessage 저장
```

외부 API 실패를 단순 서버 오류로 숨기지 않고 AI 요청 자체의 실패 상태로 관리했다.

### AI 응답 Parsing 실패

AI가 예상한 JSON 구조와 다른 값을 반환할 수 있기 때문에 JSON Parsing과 Pydantic Validation을 강화했다.

### Recommendation이 계속 PENDING으로 남는 문제

분석 과정에서 예외가 발생했을 때 실패 상태 업데이트까지 동일한 트랜잭션 영향을 받으면 상태 변경이 반영되지 않을 수 있었다.

실패 상태를 확실하게 남길 수 있도록 트랜잭션 경계를 다시 검토했다.

### Lazy Loading 오류

조회 과정에서 필요한 연관 Entity가 Transaction 종료 이후 접근되면서 Lazy Loading 문제가 발생했다.

조회 서비스의 `readOnly Transaction` 범위를 재검토했다.

### URL 본문 추출 실패

외부 사이트 구조에 따라 본문을 정상적으로 가져오지 못하는 경우가 있어 텍스트 직접 입력 fallback을 제공했다.

AI 기능은

```text
Spring
FastAPI
External AI
Database
Async Thread
External Web Page
```

가 동시에 연결되어 있기 때문에 에러 메시지만 보고 원인을 단정하기 어려웠다.

따라서 로그, 요청 상태, traceId, errorMessage를 함께 보며 문제의 위치를 좁혀나갔다.

## 아쉬웠던 점과 향후 개선 방향

### 1. Prompt Version 관리

현재 Prompt 파일을 분리했지만, 향후에는 결과 데이터와 함께 Prompt Version을 저장하면 어떤 규칙으로 생성된 결과인지 추적하기 쉬워질 것이다.

### 2. 메시지 큐 기반 비동기 처리

현재 ThreadPool 기반 비동기 구조를 다음 단계에서는 별도의 Queue 시스템으로 확장할 수 있다.

```text
Redis Queue
RabbitMQ
Amazon SQS
```

이를 통해 서버 프로세스와 AI 작업 처리의 결합도를 더 낮출 수 있다.

### 3. RAG 기반 추천 고도화

현재 핵심 분석은 Prompt Builder를 기반으로 처리한다.

향후에는 강의 설명, 자격증 정보, NCS 데이터 등을 Embedding하여 의미 기반 검색으로 확장할 수 있다.

### 4. AI 응답 품질 측정

Prompt 변경 전후의 다음 지표를 비교할 수 있다.

```text
- Parsing 실패율
- AI 요청 실패율
- 평균 응답시간
- 사용자 재분석 비율
- 추천 결과 활용률
```

### 5. AI 운영 모니터링 고도화

기능별로 다음 데이터를 확인할 수 있는 관리자 대시보드를 구성할 수 있다.

```text
- 기능별 요청 수
- 실패율
- 평균 처리시간
- Timeout 발생률
- 사용자별 요청 패턴
- AI 비용
```

## 배운 점

Module 5를 진행하면서 AI 기능은 모델 호출 코드만으로 완성되지 않는다는 것을 가장 크게 배웠다.

실제 서비스에서는 다음 요소가 함께 필요했다.

```text
요청 검증
→ 사용량 제한
→ 상태 저장
→ AI 호출
→ 응답 검증
→ 결과 저장
→ 조회
→ 실패 추적
→ 일정 기간 이후 정리
```

또한 비동기 처리에서는 메서드를 `@Async`로 실행하는 것보다 **DB commit과 Thread 실행 시점의 관계**를 이해하는 것이 더 중요했고,

AI가 생성한 결과를 서비스에 사용할 때는 자유 생성 영역과 실제 DB 데이터 영역을 명확하게 구분해야 했다.

무엇보다 AI가 결과를 만드는 것은 외부 모델의 역할이지만,

**그 요청을 언제 허용하고, 어떤 상태로 관리하며, 얼마나 보관하고, 실패했을 때 어떻게 복구할지는 결국 백엔드 서비스가 책임져야 한다.**
