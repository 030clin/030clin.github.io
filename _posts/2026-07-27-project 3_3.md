## 프로젝트 소개

Sashimi Six LMS는 **자격증 학습과 취업 준비를 하나의 흐름으로 연결하는 LMS 플랫폼**이다.

전체 프로젝트는 Module 3, 4, 5에 걸쳐 약 3개월 동안 진행되었다.

* **Module 3**에서는 전체 ERD와 백엔드 구조를 설계하고 주요 도메인의 기반을 만들었다.
* **Module 4**에서는 AI 이력서 평가와 채용공고 추천 기능을 실제 서비스 흐름에 연결하고, 외부 API와 비동기 처리 구조를 고도화했다.
* **Module 5**에서는 기존 AI 기능을 단순히 호출하고 결과를 보여주는 수준에서 벗어나, **요청부터 처리·저장·조회·실패 관리까지 운영 가능한 구조로 개선하는 것**에 집중했다.

Module 5에서 내가 담당한 주요 작업은 다음과 같다.

* AI 이력서 평가 리팩토링
* 자기소개서 AI 첨삭 기능 구현
* Spring과 FastAPI 역할 분리
* AI 요청 이력 및 최신 결과 조회 구조 설계
* 사용자별 AI 사용량 제한 정책 적용
* AI 결과 보관 정책 설계
* 채용공고 비동기 분석 트랜잭션 문제 개선
* 채용공고 URL 검증 및 SSRF 대응
* DB 기반 추천 강의 매칭 구조 개선
* 개발 DB / 운영 DB 분리 및 Flyway 운영 방식 정리
* AI 장애 및 로그 기반 문제 추적

> Module 5에서 가장 중요하게 생각한 것은
> **AI 기능을 ‘동작하는 기능’에서 ‘운영하고 관리할 수 있는 기능’으로 바꾸는 것**이었다.

## Module 5에서 마주한 핵심 문제

AI 기능은 일반적인 CRUD 기능과 다른 특성을 가지고 있었다.

* 외부 AI API 호출 비용이 발생한다.
* 응답 시간이 일정하지 않다.
* 응답 형식이 항상 동일하지 않다.
* Timeout, Quota, Billing 등의 외부 오류가 발생할 수 있다.
* 분석 시간이 긴 기능은 비동기 처리가 필요하다.
* 사용자는 과거 분석 결과를 다시 확인하고 싶어 한다.
* 실패한 요청을 추적할 수 있어야 한다.
* 반복 호출이 많아지면 비용과 서버 자원이 함께 증가한다.

Module 5에서는 자기소개서 첨삭 기능까지 추가되면서 AI 기능의 범위가 더 넓어졌다.

따라서 단순히 “AI 호출에 성공했는가?”보다 다음과 같은 질문이 중요해졌다.

1. 누가 AI 기능을 사용할 수 있는가?
2. 한 사용자가 얼마나 자주 요청할 수 있는가?
3. 요청 결과를 언제까지 보관할 것인가?
4. 실패한 요청은 어떻게 추적할 것인가?
5. 오래 걸리는 분석은 어떻게 처리할 것인가?
6. Spring과 FastAPI는 어떤 책임을 가져야 하는가?
7. DB 변경을 운영 환경에 어떻게 안전하게 반영할 것인가?

## 1. Spring과 FastAPI의 책임을 분리하다

AI 기능이 증가하면서 Spring 내부에서 인증, 데이터 조회, 프롬프트 생성, AI 호출, 응답 파싱까지 모두 처리하면 유지보수가 어려워질 수 있었다.

그래서 Module 5에서는 **AI 처리 영역을 FastAPI로 분리**하고 Spring과 역할을 나누었다.

### Spring이 담당한 역할

* 인증 및 인가
* 사용자 데이터 조회
* 요청 유효성 검증
* AI 요청 이력 저장
* 사용자별 사용량 제한
* AI 결과 저장 및 조회
* 트랜잭션 관리
* 서비스 정책 관리

### FastAPI가 담당한 역할

* Prompt Builder
* AI API 호출
* 텍스트 전처리
* AI 응답 JSON 파싱
* Pydantic 기반 응답 검증

전체 요청 흐름은 다음과 같다.

```text
Client
→ Spring Boot
→ 사용자 / 권한 / 사용량 검증
→ FastAPI
→ Prompt 생성
→ AI 분석
→ 응답 검증
→ Spring Boot
→ 결과 저장
→ Client 응답
```

이 구조를 선택한 이유는 AI 영역의 변경 주기가 일반적인 서비스 로직보다 빠르기 때문이다.

모델이나 프롬프트가 변경되어도 Spring의 핵심 비즈니스 로직이 영향을 덜 받도록 **서비스 정책과 AI 처리 책임을 분리**했다.

## 2. 프롬프트와 비즈니스 코드를 분리하다

자기소개서와 채용공고 분석 프롬프트는 기능이 고도화되면서 점점 길어졌다.

프롬프트 안에는 단순 질문뿐 아니라 다음과 같은 규칙까지 포함되었다.

* 분석 기준
* 판단 조건
* 금지 사항
* 응답 JSON 구조
* 누락 데이터 처리 기준

이를 코드 내부의 긴 문자열로 관리하면 비즈니스 로직과 프롬프트 규칙이 섞이게 된다.

그래서 프롬프트 규정을 별도 파일로 분리했다.

```text
prompt_templates/
└── job_posting_analysis_regulation.txt

prompts/
└── cover_letter_review_regulation.txt
```

FastAPI에서는 해당 파일을 읽고 사용자 입력값만 필요한 위치에 삽입하여 최종 Prompt를 생성하도록 구성했다.

이를 통해 다음과 같은 장점이 있었다.

* 코드와 프롬프트 책임 분리
* 긴 규칙의 가독성 향상
* 프롬프트 수정 시 비즈니스 코드 영향 최소화
* 향후 Prompt Version 관리로 확장 가능

프롬프트를 단순한 문자열이 아니라 **AI 기능의 운영 정책**으로 보기 시작한 것도 Module 5에서의 중요한 변화였다.

## 3. AI 요청과 결과를 이력으로 관리하다

초기 AI 기능은 사용자가 요청하면 결과를 계산해 바로 반환하는 형태가 중심이었다.

하지만 실제 서비스 흐름에서는 다음 요구사항이 생겼다.

* 페이지를 나갔다가 돌아와도 최근 결과를 다시 보고 싶다.
* 실패한 AI 요청의 원인을 확인해야 한다.
* 기능별 사용량을 확인해야 한다.
* 비동기 요청의 현재 상태를 알 수 있어야 한다.

이를 위해 AI 요청 이력 구조를 도입했다.

AI 요청에는 다음과 같은 정보를 관리하도록 설계했다.

* 사용자 ID
* AI 기능 유형
* 요청 상태
* 요청 당시 데이터 Snapshot
* AI 결과
* 실패 메시지
* 요청 시간
* 완료 시간

요청 상태는 세 가지로 구분했다.

* **PENDING** : 분석 진행 중
* **COMPLETED** : 분석 완료
* **FAILED** : 분석 실패

이제 단순히 결과만 저장하는 것이 아니라,

> **누가 어떤 AI 기능을 요청했고, 현재 어떤 상태이며, 실패했다면 왜 실패했는지**

까지 추적할 수 있게 되었다.

## 4. AI 사용량 제한 정책을 설계하다

AI 기능은 요청할 때마다 외부 API 비용이 발생한다.

따라서 일반 조회 API처럼 무제한 호출을 허용하면 짧은 시간 동안 반복 요청이 발생했을 때 비용 증가와 Rate Limit 문제가 발생할 수 있다.

Module 5에서는 사용자별 AI 사용량 제한 정책을 적용했다.

* 이력서 AI 평가 : **1시간 10회**
* 자기소개서 AI 첨삭 : **1시간 10회**
* 채용공고 AI 분석 : **1시간 10회**
* 전체 AI 기능 합산 : **1시간 30회**

1시간 단위로 제한한 이유는 정상적인 수정·재분석 흐름까지 막지 않으면서 짧은 시간의 반복 호출만 제어하기 위해서였다.

반면 이미 저장된 결과를 조회하는 GET API는 제한 대상에서 제외했다.

### 제한 대상

* AI 이력서 평가 요청
* 자기소개서 AI 첨삭 요청
* 채용공고 AI 분석 요청

### 제한 제외

* 최신 AI 결과 조회
* AI 상세 결과 조회
* 저장된 추천 결과 조회

이미 생성된 데이터를 조회하는 요청은 외부 AI 호출 비용이 발생하지 않기 때문이다.

이 작업을 통해 **AI 사용 정책 역시 백엔드가 관리해야 하는 비즈니스 규칙**이라는 점을 경험했다.

## 5. 이력서 평가에서 Backend와 AI의 역할을 분리하다

이력서 평가는 학력, 경력, 자격증을 기준으로 점수와 피드백을 제공하는 기능이다.

AI가 모든 평가를 담당하면 동일한 이력서라도 모델 응답에 따라 점수가 달라질 수 있다는 문제가 있었다.

그래서 Module 5에서는 **계산 가능한 영역과 해석이 필요한 영역을 분리**했다.

### Backend가 담당하는 영역

* 학력 점수 계산
* 경력 개수 계산
* 총 근무 기간 계산
* 자격증 개수 계산
* 평균 점수 계산
* 평가 등급 결정

### AI가 담당하는 영역

* 경력 경험의 연속성 분석
* 부족한 부분에 대한 설명
* 개선 방향 제안
* 자연어 피드백 생성

즉,

> **명확한 기준은 Backend가 계산하고, 해석이 필요한 부분만 AI가 담당하도록 했다.**

이를 통해 AI 응답이 달라져도 점수 기준은 일관되게 유지할 수 있었다.

또한 AI 호출에 실패하더라도 핵심 평가 결과 전체가 사라지지 않도록 기본 피드백 fallback도 함께 고려했다.

## 6. 자기소개서 AI 첨삭 기능을 구현하다

Module 5에서 새롭게 구현한 핵심 기능 중 하나는 **자기소개서 AI 첨삭**이다.

자기소개서는 총 5개의 문항으로 구성했다.

1. 자기 소개
2. 성격의 장점과 단점
3. 대표 프로젝트 경험
4. 문제 해결 경험
5. 상사와 의견이 다를 경우

사용자가 단순히 수정된 문장 하나만 받는 것이 아니라, 자신이 작성한 글에서 어떤 부분을 보완해야 하는지 확인할 수 있도록 결과를 구조화했다.

### 작성 페이지에서 제공하는 정보

* 작성 완료 문항 수
* 수정 필요 문항 수
* 보완 권장 문항 수
* 맞춤법 및 오타 수정 수
* 반복 표현 수
* 평균 문장 길이
* AI 종합 코멘트

### 상세 결과 페이지에서 제공하는 정보

* 문항별 상태
* 맞춤법 수정 내용
* 반복 표현
* 종합 피드백
* 개선 예시

Spring은 자기소개서 원본 데이터와 결과 저장·조회를 담당하고,
FastAPI는 AI 분석과 응답 구조 검증을 담당했다.

## 7. 채용공고 분석을 비동기 상태 기반으로 처리하다

채용공고 분석은 URL 또는 텍스트를 입력받아 다음 정보를 제공하는 기능이다.

* 채용공고 핵심 요약
* 사용자 이력서 적합도
* 부족한 역량
* 추천 자격증
* 추천 강의

외부 AI 분석에는 시간이 필요하기 때문에 요청과 실제 분석을 분리했다.

```text
사용자 요청
→ Recommendation PENDING 저장
→ recommendationId 반환
→ 비동기 AI 분석
→ 결과 저장
→ COMPLETED 또는 FAILED
→ Frontend polling
```

사용자는 POST 요청 이후 분석이 끝날 때까지 HTTP 요청을 유지하지 않는다.

대신 `recommendationId`를 받아 상태를 조회하고,
프론트에서는 `COMPLETED`가 될 때까지 polling한다.

이 구조를 통해 **오래 걸리는 AI 분석을 사용자 요청 흐름에서 분리**할 수 있었다.

## 8. 비동기 처리에서 발생한 트랜잭션 문제를 해결하다

비동기 채용공고 분석을 구현하면서 중요한 문제가 발생했다.

다음과 같이 코드가 실행되더라도 실제 DB commit이 같은 순서로 끝난다는 보장은 없었다.

```text
Recommendation 저장
→ Async 분석 실행
```

Spring의 트랜잭션 안에서는 `save()`가 호출되어도 실제 commit은 메서드가 종료될 때 이루어질 수 있다.

그 전에 비동기 Thread가 실행되면 아직 DB에 commit되지 않은 Recommendation을 조회하려 할 수 있었다.

이를 해결하기 위해 비동기 분석 시작 시점을 **트랜잭션 commit 이후**로 변경했다.

```java
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            asyncService.analyze(
                recommendationId,
                userId,
                historyId
            );
        }
    }
);
```

변경 이후 흐름은 다음과 같다.

```text
PENDING 데이터 저장
→ Transaction Commit
→ afterCommit()
→ Async 분석 시작
→ AI 호출
→ 결과 저장
```

이 경험을 통해 비동기 처리에서는 단순한 메서드 실행 순서보다
**데이터가 실제로 다른 트랜잭션에서 조회 가능한 시점을 고려하는 것이 중요하다**는 것을 배웠다.

## 9. 채용공고 URL 입력의 SSRF 위험을 방어하다

채용공고 URL 분석은 사용자가 입력한 주소로 서버가 직접 요청을 보내기 때문에 SSRF 위험이 존재한다.

악의적인 사용자가 다음과 같은 주소를 입력할 수 있다.

```text
http://localhost
http://127.0.0.1
사설 IP
link-local IP
metadata 서버 주소
```

따라서 URL 요청 전에 다음 검증을 적용했다.

### 허용

* `http`
* `https`

### 차단

* localhost
* loopback
* private network
* link-local
* metadata IP

또한 다음과 같은 방어 정책도 적용했다.

* scheme이 없는 URL은 `https` 기준으로 보정
* redirect 이후 최종 URL 재검증
* Jsoup timeout 설정
* 지나치게 짧은 본문 차단
* 본문 추출 실패 시 AI 호출 중단

일부 사이트는 크롤링 구조상 본문 추출이 어려웠다.

이 경우 보안 정책을 억지로 우회하기보다 **텍스트 직접 입력이라는 대체 경로를 제공하는 방식**을 선택했다.

---

## 10. 추천 강의는 AI가 직접 생성하지 않도록 했다

채용공고 분석 결과에는 사용자에게 필요한 강의 추천도 포함된다.

하지만 AI가 강의명을 직접 생성하면 실제 LMS에 존재하지 않는 강의를 만들어낼 수 있다.

그래서 AI는 실제 강의명이 아니라 **강의를 찾기 위한 기준만 생성**하도록 했다.

```text
AI
→ courseSearchCriteria 생성

Spring
→ LMS DB 조회

DB
→ 실제 존재하는 승인 강의 반환
```

즉,

> **AI는 무엇을 찾을지 결정하고, Backend는 실제 존재하는 데이터를 검증해 반환한다.**

생성형 AI의 장점은 활용하면서도, 최종 사용자에게는 검증된 내부 데이터만 제공하도록 설계했다.

---

## 11. AI 결과의 보관 기간을 정책으로 관리하다

AI 결과를 무기한 저장하면 시간이 지날수록 DB 용량이 계속 증가한다.

반대로 분석 직후 바로 삭제하면 사용자는 최근 결과를 다시 확인할 수 없다.

따라서 Module 5에서는 **AI 결과를 일정 기간 동안만 보관하는 정책**을 설계했다.

보관 기간은 **7일**로 설정했다.

이 정책은 단순히 데이터를 삭제하는 문제가 아니라,

* 사용자의 재조회 편의성
* 저장 공간
* 개인정보 보관 범위
* 운영 비용

을 함께 고려한 결정이었다.

---

## 12. 개발 DB와 운영 DB를 분리하다

Module 5에서는 AI 요청 이력, 자기소개서 첨삭 결과 등 새로운 데이터 구조가 추가되면서 migration 작업도 잦아졌다.

개발 과정의 migration을 운영·시연 DB에 바로 자동 적용하면 기존 데이터가 영향을 받을 수 있었다.

그래서 DB를 목적에 따라 분리했다.

### 개발 DB

**sixsashimi_dev**

* 개발 및 테스트 전용
* local profile 사용
* Flyway 자동 실행
* migration 검증
* Dummy Data 사용 가능

### 운영·시연 DB

**sixsashimi_db**

* prod profile 사용
* 기존 데이터 유지
* Flyway 자동 실행 비활성화
* 검증된 SQL만 수동 반영

DB 변경 흐름은 다음과 같이 정리했다.

```text
Migration 작성
→ DEV DB 자동 반영
→ 팀 테스트
→ DBA 검토
→ PROD SQL 수동 적용
```

이를 통해 **개발 중 스키마 검증과 운영 데이터 보호를 분리**할 수 있었다.

---

## 13. 운영 환경에서 발생한 문제를 로그와 상태값으로 추적하다

Module 5에서는 배포 이후 실제 AI 호출을 테스트하면서 여러 문제가 발생했다.

### AI Quota / Billing 오류

외부 AI 서비스에서 `429` 응답이 발생하면 요청 상태를 `FAILED`로 변경하고 실패 원인을 저장했다.

### AI 응답 Parsing 실패

AI가 예상한 JSON 구조와 다른 값을 반환할 수 있어 JSON Parsing과 Pydantic Validation을 강화했다.

### Recommendation이 계속 PENDING인 문제

비동기 분석 과정에서 예외가 발생했지만 실패 상태 갱신까지 정상적으로 반영되지 않는 상황이 있었다.

실패 상태를 확실히 기록할 수 있도록 트랜잭션 경계를 다시 검토했다.

### Lazy Loading 오류

조회 과정에서 필요한 연관 Entity를 Transaction 종료 후 접근하면서 문제가 발생해 `readOnly Transaction` 범위를 재검토했다.

### URL 본문 추출 실패

외부 사이트 구조에 따라 본문을 정상적으로 가져오지 못하는 경우에는 텍스트 직접 입력을 안내했다.

AI 기능은 다음 여러 요소가 동시에 연결되어 있다.

```text
Spring
→ FastAPI
→ External AI
→ Database
→ Async Thread
→ External Web Page
```

따라서 한 번의 오류만 보고 원인을 단정하기보다,

**status, errorMessage, traceId, 서버 로그를 함께 확인하며 문제의 위치를 좁혀나가는 방식**이 중요했다.

## 아쉬웠던 점과 향후 개선 방향

### Prompt Version 관리

현재 프롬프트 파일을 코드와 분리했지만, 앞으로는 결과와 함께 Prompt Version을 저장하면 어떤 규칙으로 생성된 결과인지 더 쉽게 추적할 수 있다.

### 메시지 큐 기반 비동기 처리

현재 ThreadPool 기반 비동기 구조를 다음 단계에서는 Redis Queue, RabbitMQ, SQS 등의 메시지 큐로 확장할 수 있다.

서버와 AI 작업 처리의 결합도를 더 낮출 수 있을 것이다.

### RAG 기반 추천 고도화

현재 핵심 분석은 Prompt 기반으로 동작한다.

향후 강의 설명, 자격증 정보, NCS 데이터를 Embedding하여 의미 기반 검색으로 확장할 수 있다.

### AI 응답 품질 측정

프롬프트 변경 전후에 다음과 같은 지표를 비교할 수 있다.

* Parsing 실패율
* AI 요청 실패율
* 평균 응답 시간
* 사용자 재분석 비율
* 추천 결과 활용률

### AI 운영 모니터링 고도화

기능별로 다음 정보를 확인할 수 있는 관리자 대시보드로 확장할 수 있다.

* 기능별 요청 수
* 실패율
* 평균 처리 시간
* Timeout 발생률
* 사용자별 요청 패턴
* AI API 비용

## 배운 점

Module 5를 진행하면서 AI 기능은 단순히 모델 API를 호출하는 것만으로 완성되지 않는다는 점을 가장 크게 배웠다.

실제 서비스에서는 다음 흐름 전체를 관리해야 했다.

```text
요청 검증
→ 사용량 제한
→ 상태 저장
→ AI 호출
→ 응답 검증
→ 결과 저장
→ 결과 조회
→ 실패 추적
→ 보관 기간 이후 정리
```

또한 비동기 처리에서는 단순히 `@Async`를 사용하는 것보다 **DB commit 시점과 별도 Thread 실행 시점의 관계를 이해하는 것**이 중요했다.

AI가 생성한 결과 역시 그대로 사용하는 것이 아니라,
실제 DB 데이터와 검증 가능한 정보의 경계를 분명하게 나누어야 했다.

무엇보다 AI가 결과를 만드는 것은 외부 모델의 역할이지만,

> **그 요청을 언제 허용하고, 어떤 상태로 관리하며, 얼마나 보관하고, 실패했을 때 어떻게 대응할지는 결국 백엔드 서비스가 책임져야 한다.**
