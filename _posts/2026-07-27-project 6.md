## 프로젝트 소개

CampFlow는 부트캠프의 훈련생·강사·운영 매니저가 사용하는 **교육 운영 통합 그룹웨어 서비스**다.

기존 부트캠프 운영에서는 출결, 공지, 상담, 팀 관리, 결재, 일정 등의 업무가 여러 도구에 분산되어 있고, 담당자가 반복적으로 데이터를 확인하거나 전달해야 하는 문제가 있었다.

이번 프로젝트에서는 이러한 업무를 하나의 서비스 안에서 연결하고, 단순히 기능을 구현하는 것을 넘어 **실제 운영 과정에서 데이터가 안전하게 유지되고 외부 서비스 장애에도 핵심 업무가 영향을 받지 않는 구조**를 만드는 것을 목표로 했다.

내가 주로 담당한 영역은 크게 두 가지였다.

- **전자결재**: 전자서명, 휴가·구매 결재, 승인/반려, 결재 이력, 휴가 신청서 PDF, 예산 Google Sheets 연동
- **팀 관리**: 프로젝트 기간별 팀 구성, 팀원 배정, 팀 변경, Sendbird 채팅방 연동, Notion 팀 페이지 연동 및 외부 연동 안정화

이번 프로젝트에서 가장 많이 고민했던 것은 기능 자체보다 **"정상적인 상황뿐 아니라 동시에 요청이 들어오거나 외부 API가 실패해도 데이터가 깨지지 않게 하려면 어떻게 해야 하는가"**였다.

---

## 1. 전자결재 - 단순 CRUD보다 중요한 것은 상태의 무결성이었다

전자결재는 처음 보면 문서를 작성하고 관리자가 승인하거나 반려하는 CRUD 기능처럼 보인다.

하지만 실제 구현에서는 그렇지 않았다.

결재 문서에는 다음과 같은 상태 흐름이 존재한다.

```text
DRAFT → PENDING → APPROVED / REJECTED
```

여기서 중요한 것은 단순히 상태값을 변경하는 것이 아니라 다음과 같은 상황까지 고려하는 것이었다.

- 승인 권한이 있는 사용자인가?
- 이미 처리된 문서를 다시 승인할 수 있는가?
- 동시에 두 명이 승인하면 어떻게 되는가?
- 승인 당시 사용한 서명을 이후에도 동일하게 보존할 수 있는가?
- 외부 데이터가 변경되어도 당시 결재 내용은 유지되는가?

전자결재를 구현하면서 **상태를 가진 데이터에서는 API 개수보다 상태 전이 규칙과 데이터 무결성이 더 중요하다**는 것을 경험했다.

---

## 2. 동시 승인 문제 - 조회 후 UPDATE만으로는 부족했다

결재 처리에서 특히 신경 쓴 부분은 동시성이었다.

일반적으로는 결재 문서를 조회하고 현재 상태가 `PENDING`인지 확인한 뒤 `APPROVED`로 변경하는 방식으로 구현할 수 있다.

하지만 두 관리자가 거의 동시에 같은 결재 문서를 승인한다면 문제가 생길 수 있다.

```text
관리자 A → PENDING 조회
관리자 B → PENDING 조회

관리자 A → APPROVED
관리자 B → APPROVED
```

두 요청 모두 조회 시점에는 정상적인 `PENDING` 상태를 확인했기 때문에 애플리케이션의 `if`문만으로는 **조회와 수정 사이에서 발생하는 경쟁 상태**를 완전히 막기 어렵다.

그래서 결재 처리에서는 현재 상태까지 UPDATE 조건에 포함하는 **조건부 UPDATE 방식**을 적용했다.

```sql
UPDATE approval
SET status = 'APPROVED'
WHERE approval_id = ?
  AND status = 'PENDING';
```

UPDATE 결과가 1건이면 정상적으로 처리된 것이고, 0건이면 이미 다른 요청에서 상태가 변경된 것으로 판단할 수 있다.

기존의

```text
상태 조회
→ 상태 확인
→ 수정
```

방식에서 한 단계 더 나아가,

```text
현재 상태가 PENDING인 데이터만 수정
→ 실제 변경된 Row 수 확인
```

하도록 DB에서도 상태 전이를 보호했다.

이를 통해 **비즈니스 로직의 검증과 DB 수준의 조건을 함께 사용해 중복 승인 가능성을 줄였다.**

## 3. 전자서명 - 현재 서명이 아니라 '승인 당시의 서명'을 남기기

전자결재에는 사용자의 전자서명이 사용된다.

처음에는 결재 데이터에서 사용자의 현재 전자서명을 참조하는 방식도 생각할 수 있었다.

하지만 사용자가 결재를 승인한 이후 자신의 전자서명을 변경하거나 삭제한다면, 과거 결재 문서까지 현재 서명의 영향을 받을 수 있다는 문제가 있었다.

결재 문서에서 중요한 것은 **지금 사용자의 서명이 무엇인가가 아니라, 승인 당시 어떤 서명을 사용했는가**다.

그래서 결재 시점의 서명 정보를 Snapshot으로 남기는 방향으로 설계했다.

```text
사용자 전자서명
      ↓
결재 승인
      ↓
승인 시점 서명 Snapshot 저장
      ↓
이후 사용자가 서명을 변경해도
기존 결재 문서에는 영향 없음
```

이 경험을 통해 이력성 데이터에서는 단순 FK 참조보다 **"그 당시의 상태를 보존해야 하는가"**를 먼저 판단해야 한다는 것을 배웠다.

## 4. 휴가 신청서 - HTML Template에서 PDF 문서까지

전자결재에는 휴가 신청 기능도 포함되었다.

휴가 신청이 최종 승인되면 단순히 상태만 `APPROVED`로 변경하는 것이 아니라 실제 운영에서 사용할 수 있는 휴가 신청서를 PDF 형태로 생성하도록 구성했다.

전체 흐름은 다음과 같다.

```text
휴가 신청
→ 결재 요청
→ 승인
→ 결재 데이터 조회
→ 휴가 신청서 Template 구성
→ PDF 생성
```

PDF에는 신청자의 정보와 휴가 기간, 휴가 유형, 신청 내용 등 결재 당시의 데이터를 반영했다.

이 과정에서 PDF 생성 자체보다 **어떤 데이터를 어느 시점의 기준으로 문서에 남길 것인지**가 더 중요했다.

결재 이후 사용자 정보나 원본 데이터가 변경되더라도 이미 승인된 문서는 당시의 내용을 표현해야 하기 때문이다.

## 5. Google Sheets 연동 - 외부 데이터를 매번 직접 조회하지 않기

전자결재의 구매 요청에서는 예산 정보를 확인해야 했다.

부트캠프 운영 과정에서 관리하는 Google Sheets의 예산 데이터를 CampFlow와 연결했는데, 처음에는 화면 요청마다 Google Sheets API를 호출하는 방법도 고려할 수 있었다.

하지만 외부 API를 실시간 조회 구조에 직접 넣으면 다음과 같은 문제가 생길 수 있다.

- Google API 장애가 CampFlow 조회 실패로 이어질 수 있음
- 같은 데이터를 반복해서 외부 API에서 조회
- API 호출량 증가
- 응답 속도가 외부 서비스 상태에 의존
- Sheet 컬럼 변경에 서비스가 직접 영향을 받을 수 있음

그래서 Google Sheets를 서비스의 실시간 DB처럼 사용하지 않고 다음과 같은 구조로 가져갔다.

```text
Google Sheets
      ↓
데이터 동기화
      ↓
CampFlow DB Snapshot
      ↓
전자결재에서 DB 데이터 조회
```

또한 Sheet마다 컬럼 이름이 완전히 동일하다는 보장이 없었기 때문에 외부 컬럼을 CampFlow 내부 표준 필드로 매핑했다.

```text
category
budgetAmount
usedAmount
remainingAmount
```

외부 시스템의 데이터 구조를 그대로 내부 도메인까지 전달하는 것이 아니라, **외부 데이터를 내부 서비스가 이해하는 구조로 한 번 변환하는 계층이 필요하다**는 것을 경험했다.

## 6. 팀 관리 - 현재 팀만 저장해서는 해결되지 않았다

두 번째 핵심 담당 기능은 팀 관리였다.

CampFlow에서는 프로젝트가 한 번으로 끝나는 것이 아니라 여러 기간에 걸쳐 운영될 수 있기 때문에 단순히 `Team`과 `Member`만 저장하는 것으로는 부족했다.

예를 들어 새로운 프로젝트가 시작됐다고 해서 이전 프로젝트의 팀 구성을 덮어쓰면 과거 팀 정보를 확인할 수 없게 된다.

그래서 팀을 **기간(TeamPeriod)** 기준으로 관리했다.

```text
TeamPeriod
   ↓
Team
   ↓
TeamMember
```

이를 통해 현재 팀뿐 아니라 프로젝트 기간별 팀 구성을 구분할 수 있도록 했다.

팀 이동이나 재배정에서도 기존 데이터를 무조건 삭제하기보다 상태와 기간을 기준으로 관리하면서 **현재 상태와 과거 이력을 함께 유지하는 것**을 중요하게 봤다.

이 과정에서 `archivedAt`과 `deletedAt`의 의미도 분리했다.

- `archivedAt`: 운영 기간이 끝나 더 이상 활성 상태가 아님
- `deletedAt`: 실제 삭제 처리된 데이터

둘을 같은 의미로 사용하면 정상적으로 종료된 과거 데이터와 삭제된 데이터를 구분하기 어려워진다.

단순한 컬럼 하나의 차이처럼 보였지만, 운영 데이터를 다루면서 **상태의 의미를 명확하게 정의하는 것이 조회 로직과 데이터 보존 정책 전체에 영향을 준다**는 것을 알게 됐다.

## 7. 팀 생성과 Sendbird·Notion 연동

팀 구성이 완료되면 필요에 따라 외부 협업 도구도 함께 생성되도록 했다.

```text
팀 구성 저장
      ↓
Sendbird 단체 채팅방 생성
      ↓
Notion 팀 페이지 생성
```

사용자는 팀 구성 시 옵션을 선택할 수 있고, 이에 따라 팀별 협업 공간을 자동으로 만들 수 있도록 구성했다.

하지만 여기서 중요한 문제가 있었다.

**DB 저장과 외부 API 호출은 하나의 트랜잭션으로 묶을 수 없다는 것**이다.

예를 들어 다음과 같은 상황이 발생할 수 있다.

```text
DB 팀 생성 성공
→ Sendbird 성공
→ Notion 실패
```

반대로 외부 API를 먼저 호출했는데 DB 저장이 실패하면 외부 서비스에는 존재하지만 CampFlow에는 존재하지 않는 데이터가 생길 수도 있다.

처음에는 트랜잭션이 성공한 뒤 외부 API를 호출하도록 `AFTER_COMMIT`을 사용했다.

```text
DB Transaction
→ Team 저장
→ COMMIT
→ AFTER_COMMIT
→ Sendbird / Notion 호출
```

이를 통해 적어도 **DB가 Rollback됐는데 외부 리소스만 생성되는 문제**는 막을 수 있었다.

하지만 이것만으로는 충분하지 않았다.

---

## 8. AFTER_COMMIT에서 Outbox 구조로

`AFTER_COMMIT`은 DB가 정상적으로 저장된 이후 외부 API를 호출할 수 있다는 장점이 있다.

하지만 외부 API 호출 자체가 실패하면 문제가 남는다.

```text
DB Commit 성공
→ AFTER_COMMIT 실행
→ Notion API 실패
→ DB에는 팀 존재
→ Notion 페이지 없음
```

단순히 로그만 남긴다면 이후 어떤 작업이 실패했는지 확인하고 수동으로 복구해야 한다.

그래서 외부 연동 작업 자체를 DB에 저장하는 **Outbox 구조**로 확장했다.

```text
팀 생성 Transaction

Team 저장
+
Outbox Event 저장

        ↓ COMMIT

Outbox Processor
        ↓
Sendbird / Notion 호출
        ↓
성공 → 완료 처리
실패 → 재시도 가능
```

핵심은 **외부 API 요청도 하나의 관리 가능한 데이터로 취급한 것**이다.

외부 연동이 실패해도 CampFlow의 핵심 데이터는 이미 정상적으로 저장되어 있고, 실패한 작업은 Outbox를 통해 다시 시도할 수 있다.

이 구조를 적용하면서 외부 API 장애를 **서비스 전체의 실패가 아니라 재처리 가능한 작업의 실패**로 바꿀 수 있었다.

## 9. Outbox도 동시 실행을 고려해야 했다

Outbox를 만들었다고 해서 문제가 모두 해결되는 것은 아니었다.

스케줄러나 여러 서버 인스턴스가 같은 Outbox 이벤트를 동시에 조회하면 하나의 작업이 중복 실행될 가능성이 있다.

특히 외부 API 호출은 단순 DB 조회와 다르게 실제 리소스를 생성할 수 있기 때문에 중복 실행에 더 민감하다.

그래서 처리 중인 작업을 구분하기 위한 `processingToken`과 JPA `@Version`을 이용해 **동시에 같은 이벤트를 처리하는 상황을 방어하는 구조**를 적용했다.

```text
PENDING Event
     ↓
처리 대상 선점
     ↓
processingToken 발급
     ↓
외부 API 호출
     ↓
SUCCESS

실패 시
     ↓
retryCount 증가
     ↓
재시도
```

이 과정에서 단순한 Retry만 추가하는 것보다,

- 누가 이 작업을 처리하고 있는가?
- 같은 작업이 동시에 실행될 수 있는가?
- 몇 번까지 다시 시도할 것인가?
- 반복적으로 실패한 작업을 어떻게 관리할 것인가?

까지 함께 설계해야 안정적인 재처리 구조가 된다는 것을 배웠다.

## 10. Notion 연동 - Create가 아니라 Upsert로

Notion 팀 페이지 연동에서도 단순히 API 호출에 성공하는 것만으로는 부족했다.

팀 정보가 변경될 때마다 새로운 페이지를 생성한다면 동일한 팀의 페이지가 계속 늘어날 수 있기 때문이다.

그래서 `TeamId`를 기준으로 기존 페이지의 존재 여부를 확인하고,

```text
페이지 없음 → CREATE
페이지 있음 → UPDATE
```

하는 Upsert 방식으로 구성했다.

이를 통해 팀 정보가 변경되더라도 동일한 팀에 대한 Notion 페이지가 중복 생성되지 않도록 했다.

이 경험을 통해 외부 시스템과 데이터를 동기화할 때는 단순 CRUD보다 **내부 데이터와 외부 리소스를 연결할 수 있는 식별 기준**을 먼저 정하는 것이 중요하다는 것을 알게 됐다.

---

## 11. CodeRabbit 리뷰를 '정답'이 아니라 검증 수단으로 사용하기

프로젝트에서는 CodeRabbit을 통해 코드 리뷰도 진행했다.

다만 리뷰 내용을 모두 그대로 반영하지는 않았다.

리뷰 내용 중에서도 다음과 같은 부분은 우선적으로 확인했다.

- 보안 문제
- 데이터 무결성 문제
- 런타임 오류 가능성
- 동시성 문제
- 외부 API 장애 가능성

반면 현재 서비스 정책이나 MVP 범위와 맞지 않는 제안은 그대로 적용하지 않고 실제 서비스 흐름에 맞는지 다시 판단했다.

자동 리뷰 도구가 문제 가능성을 빠르게 발견하는 데는 도움이 됐지만, **최종적으로 그 제안이 현재 서비스 정책과 구조에 맞는지는 개발자가 판단해야 한다**는 점을 경험했다.

---

## 프로젝트에서 기여한 결과

이번 프로젝트에서는 전자결재와 팀 관리라는 서로 다른 기능을 담당했지만, 두 기능에서 공통적으로 중요하게 생각한 것은 **운영 과정에서 데이터가 깨지지 않는 구조**였다.

### 전자결재

- 결재 상태 전이 규칙 정리
- 조건부 UPDATE를 통한 중복 승인 방어
- 전자서명 Snapshot 보존
- 휴가 신청서 PDF 생성
- Google Sheets 예산 데이터 연동
- 외부 데이터의 내부 표준 구조 변환

### 팀 관리

- 기간 기반 팀 구성 및 팀원 배정
- 팀 변경 및 과거 데이터 보존
- Sendbird 채팅방 연동
- Notion 팀 페이지 연동
- Notion TeamId 기반 Upsert
- AFTER_COMMIT 기반 외부 연동 분리
- Outbox 기반 실패 작업 재처리
- `processingToken`, `@Version`을 통한 중복 처리 방어

결과적으로 단순히 **"팀을 만들면 채팅방을 생성한다", "결재 버튼을 누르면 승인된다"** 수준에서 끝내지 않고, 동시 요청·외부 API 실패·데이터 변경까지 고려한 백엔드 구조를 경험할 수 있었다.

## 아쉬웠던 점과 개선 방향

이번 프로젝트에서는 한 달이라는 제한된 기간 안에서 핵심 기능의 구현과 안정화에 집중했다.

Outbox 구조 역시 재시도가 가능한 수준까지 구현했지만, 실제 운영 환경이라면 더 발전시킬 부분이 있다.

### 1. Outbox 처리 구조 고도화

현재 구조에서 더 나아간다면 RabbitMQ나 Kafka와 같은 메시지 브로커를 활용해 외부 연동 작업을 분리할 수 있다.

또한 Retry 횟수를 모두 소진한 이벤트를 별도로 관리하고 운영자가 확인하거나 재처리할 수 있는 관리 기능도 필요하다.

### 2. 외부 연동 모니터링 강화

Sendbird, Notion, Google Sheets처럼 여러 외부 서비스를 사용하기 때문에 서비스별 성공률, 실패 횟수, 재시도 횟수 등을 메트릭으로 관리하면 장애 원인을 더 빠르게 파악할 수 있다.

### 3. 동시성 테스트 확대

전자결재의 조건부 UPDATE와 Outbox의 중복 처리 방어를 구현했지만, 더 많은 동시 요청을 발생시키는 부하 테스트를 통해 실제 경쟁 상황에서의 동작을 추가로 검증할 수 있다.

## 배운 점

이번 프로젝트에서 가장 크게 배운 것은 **"정상적으로 한 번 실행되는 코드"와 "운영 가능한 코드"는 다르다**는 점이었다.

전자결재에서는 동시에 요청이 들어올 수 있었고, 팀 관리에서는 DB 저장이 성공해도 Sendbird나 Notion 호출이 실패할 수 있었다.

Google Sheets의 데이터 구조가 바뀔 수도 있었고, 사용자가 전자서명을 변경해도 과거 결재 기록은 유지되어야 했다.

이러한 문제를 해결하면서 백엔드에서는 성공 흐름만 만드는 것이 아니라 다음과 같은 상황을 함께 고려해야 한다는 것을 배웠다.

```text
동시에 실행되면?
중간에 실패하면?
다시 실행되면?
외부 서비스가 응답하지 않으면?
데이터가 나중에 변경되면?
```

특히

```text
AFTER_COMMIT
→ Outbox
→ Retry
→ 중복 처리 방어
```

로 구조를 발전시킨 과정은 이번 프로젝트에서 가장 의미 있었던 경험이었다.

외부 API를 연결하는 것 자체보다, **외부 API가 실패해도 내부 핵심 데이터와 서비스 흐름을 지킬 수 있는 구조를 만드는 것**이 더 중요했다.
