## 프로젝트 소개

Sashimi Six LMS는 자격증 학습과 취업 준비를 연결하는 LMS 플랫폼이다.

전체 프로젝트는 Module 3, 4, 5에 걸쳐 약 3개월 동안 진행되며,  
Module 3에서는 이후 기능 개발의 기반이 되는 백엔드 구조와 데이터 모델을 설계하고 주요 기능의 1차 구현을 진행했다.

나는 Module 3에서 **BE·DBA 역할**을 맡았다.

특정 API 하나만 구현하는 역할보다 프로젝트 전반의 기준을 정리하는 일에 집중했다.

- 전체 ERD 초안 설계 및 변경 관리
- 도메인별 데이터 구조와 관계 정의
- 클린 아키텍처 기반 패키지 구조 정리
- API 요청부터 DB 저장까지의 데이터 흐름 정리
- Swagger 기반 API 명세와 협업 환경 구성
- 공통 예외 처리 및 traceId 구조 분석
- JWT 인증·인가 흐름 정리
- 이메일 인증 기술 선택과 구조 설계
- AI 기능의 Port-Adapter 구조 및 비동기 처리 설계
- 데이터 정합성 및 동시성 검토
- Flyway 기반 DB 마이그레이션 관리
- 기술 발표 자료와 문서화

Module 3에서 가장 중요하게 생각한 것은  
**기능이 추가되고 요구사항이 바뀌더라도 전체 데이터와 백엔드 구조가 쉽게 흔들리지 않도록 기준을 만드는 것**이었다.

## Module 3에서 마주한 핵심 문제

프로젝트 초기에는 각 기능의 요구사항이 계속 구체화되는 단계였다.

회원, 강의, 수강, 장바구니, 결제, 크레딧, 이력서, 추천, 이메일 인증처럼 서로 연결된 기능이 많았기 때문에, 각 담당자가 자신의 기능만 기준으로 테이블과 API를 설계하면 다음과 같은 문제가 발생할 수 있었다.

- 동일한 데이터가 여러 테이블에 중복 저장될 수 있음
- 도메인 간 관계와 책임이 불분명해질 수 있음
- 한 기능의 변경이 다른 기능에 예상하지 못한 영향을 줄 수 있음
- 프론트엔드와 백엔드의 API 요청·응답 기준이 달라질 수 있음
- 팀원별 로컬 DB 구조가 달라질 수 있음
- 인증, 예외 처리, 외부 API 호출 방식이 도메인마다 달라질 수 있음

따라서 Module 3에서는 개별 기능 개발과 함께  
**데이터 모델, 도메인 경계, 공통 처리 방식, API 계약을 먼저 정리할 필요가 있었다.**

## 1. 전체 ERD 초안 설계와 데이터 구조 관리

Module 3에서 가장 중심적으로 맡은 역할은 프로젝트 전체 ERD를 설계하고 관리하는 일이었다.

주요 도메인을 기준으로 필요한 테이블을 먼저 구분했다.

- 회원과 인증
- 이메일 인증
- 강의와 카테고리
- 수강과 진도
- 장바구니
- 결제와 크레딧
- 이력서
- 채용공고 추천
- AI 분석 결과

각 기능 담당자가 개별적으로 테이블을 설계하는 대신, 전체 기능 흐름을 먼저 확인하고 다음 기준으로 관계를 검토했다.

### ERD 설계 기준

1. 하나의 데이터가 여러 테이블에 불필요하게 중복되지 않는가
2. 각 테이블의 책임이 명확한가
3. 도메인 간 연관관계가 지나치게 강하게 연결되어 있지 않은가
4. 중복 데이터와 잘못된 상태 전이를 막을 제약조건이 있는가
5. 기능 변경이 발생해도 확장 가능한 구조인가
6. 결제·크레딧처럼 정확성이 중요한 데이터의 정합성이 보장되는가

요구사항이 변경될 때마다 단순히 컬럼을 추가하는 것이 아니라,  
해당 변경이 다른 테이블과 기능에 어떤 영향을 미치는지 함께 검토했다.

이를 통해 ERD를 단순한 설계 결과물이 아니라  
**팀 전체가 백엔드 구현 방향을 맞추는 공통 기준**으로 활용하고자 했다.

## 2. 도메인별 책임과 패키지 구조 정리

백엔드는 다음과 같이 기능별 도메인으로 구분되어 있었다.

```text
auth
user
verification
course
category
cart
credit
payment
enrollment
resume
recommendation
security
global
token
```

기능이 많아질수록 모든 로직을 하나의 패키지에 모아두면 특정 기능을 수정할 때 영향 범위를 파악하기 어려워진다.

따라서 다음 기준으로 각 도메인의 책임을 구분했다.

- `auth`: 로그인 및 인증 진입 흐름
- `user`: 회원 정보와 사용자 도메인
- `verification`: 이메일 인증
- `course`: 강의
- `cart`: 장바구니
- `payment`: 결제
- `credit`: 크레딧
- `enrollment`: 수강
- `resume`: 이력서
- `recommendation`: 채용공고 및 AI 추천
- `security`: Spring Security와 인증 필터
- `token`: JWT 발급 및 갱신
- `global`: 공통 설정, 예외 처리, 요청 추적

도메인 분리는 단순한 폴더 정리가 아니다.

각 기능의 책임과 경계를 분명하게 만들어  
**한 도메인의 변경이 다른 도메인으로 무분별하게 전파되지 않도록 하는 설계 기준**이다.

## 3. 클린 아키텍처 기반 계층 구조 정리

여러 도메인에서는 다음과 같은 계층 구조를 사용했다.

```text
presentation
application
domain
infrastructure
```

각 계층은 서로 다른 책임을 가진다.

### presentation

사용자의 HTTP 요청을 받고 응답을 반환한다.

- Controller
- Request DTO
- Response DTO

### application

유스케이스를 실행하고 비즈니스 흐름을 조정한다.

- Service
- UseCase
- Command
- Query
- Policy
- Port

### domain

비즈니스 규칙과 핵심 모델을 표현한다.

- Domain Model
- Repository Interface
- Domain Policy

### infrastructure

DB 또는 외부 서비스와 실제로 통신한다.

- JPA Entity
- Spring Data JPA Repository
- Repository Adapter
- 외부 API Adapter

이 구조에서 중요하게 본 점은  
**API 형식, 비즈니스 모델, DB 저장 구조를 서로 분리하는 것**이었다.

예를 들어 Request DTO를 곧바로 JPA Entity로 저장하면 API 변경이 DB 구조에 직접 영향을 줄 수 있다. 반대로 Command와 Domain Model을 거치도록 하면 각 계층의 변경 영향을 줄일 수 있다.

---

## 4. API 요청부터 DB 저장까지의 데이터 흐름

Module 3에서 정리한 기본 데이터 흐름은 다음과 같다.

```text
Request DTO
→ Command 또는 Query
→ Application Service
→ Domain Model
→ Repository Interface
→ Repository Adapter
→ JPA Entity
→ Database
```

각 객체는 비슷해 보이지만 목적이 다르다.

- Request DTO: 클라이언트가 전달한 API 입력값
- Command: 특정 유스케이스를 수행하기 위한 입력 데이터
- Domain Model: 비즈니스 규칙을 가진 핵심 객체
- JPA Entity: 관계형 DB 저장을 위한 영속성 객체

이처럼 객체의 책임을 나누면서 다음과 같은 효과를 기대할 수 있었다.

- API 명세가 변경되어도 도메인 모델에 미치는 영향 감소
- DB 테이블이 변경되어도 비즈니스 로직에 미치는 영향 감소
- 테스트에서 DB 없이 도메인 규칙 검증 가능
- 외부 기술을 교체할 때 수정 범위 축소

## 5. Swagger를 API 계약 도구로 활용

프론트엔드와 백엔드가 함께 작업할 때 중요한 것은  
API가 존재하는 것보다 **서로 동일한 요청과 응답 형식을 이해하는 것**이었다.

Module 3에서는 Swagger를 사용해 다음 내용을 공유했다.

- API 경로
- HTTP Method
- Path Variable
- Request Body
- Response Body
- 인증 필요 여부
- 에러 응답 형식

`OpenApiConfig`에서는 API 문서의 제목, 설명, 버전을 설정하고 JWT Bearer 인증 방식을 등록했다.

Spring Security 환경에서도 Swagger를 사용할 수 있도록 다음 경로를 허용했다.

```text
/swagger-ui/**
/v3/api-docs/**
```

Swagger 화면에서 JWT Access Token을 입력하면 인증이 필요한 API도 직접 테스트할 수 있었다.

Notion 명세서는 기능 정책과 협업 내용을 정리하는 문서로 활용하고,  
Swagger는 실제 구현된 API를 확인하고 테스트하는 도구로 활용했다.

즉, Swagger는 단순한 자동 문서가 아니라  
**프론트엔드와 백엔드가 API 계약을 검증하는 협업 도구**였다.

## 6. 공통 예외 처리와 traceId 기반 요청 추적

공통 기능은 `global` 패키지로 분리했다.

```text
global
├── config
├── exception
└── trace
```

### 공통 예외 처리 흐름

비즈니스 로직에서 오류가 발생하면 다음 흐름으로 응답이 만들어진다.

```text
Business Logic
→ BusinessException 발생
→ GlobalExceptionHandler 처리
→ ErrorCode 조회
→ ErrorResponse 반환
```

`ErrorCode`에서는 다음 정보를 enum으로 관리한다.

- HTTP Status
- 내부 에러 코드
- 사용자에게 전달할 메시지

이를 통해 Controller마다 서로 다른 방식으로 에러를 반환하지 않고, 프론트엔드가 일관된 응답 구조를 기준으로 오류를 처리할 수 있도록 했다.

### traceId 흐름

```text
HTTP Request
→ TraceIdFilter
→ UUID traceId 생성
→ Request Attribute 저장
→ MDC 등록
→ Response Header에 X-Trace-Id 추가
```

traceId를 사용하면 클라이언트가 받은 오류 응답과 서버 로그를 연결할 수 있다.

이는 단순히 로그를 더 많이 남기는 것이 아니라,  
**여러 요청 중 특정 요청의 처리 흐름을 빠르게 추적하기 위한 운영 구조**다.

## 7. JWT 기반 인증·인가 흐름 정리

인증 구조는 Spring Security와 JWT 기반으로 구성했다.

기본 흐름은 다음과 같다.

```text
로그인 요청
→ AuthenticationManager 인증
→ JwtTokenProvider가 Access/Refresh Token 발급
→ Refresh Token 저장
→ 이후 요청에서 Bearer Token 전달
→ JwtAuthenticationFilter가 토큰 검증
→ SecurityContext에 인증 정보 저장
→ Controller 접근
```

JWT를 사용해 서버가 세션 상태를 직접 보관하지 않는 stateless 구조를 적용했다.

또한 관리자, 강사, 일반 사용자 권한을 분리해  
사용자의 역할에 따라 접근 가능한 기능을 구분했다.

로그아웃 시에는 Refresh Token을 제거하고, 이미 발급된 Access Token이 남은 시간 동안 재사용되지 않도록 블랙리스트 처리할 수 있는 구조도 함께 검토했다.

Redis는 다음과 같은 데이터에 활용할 수 있도록 고려했다.

- Refresh Token
- Access Token blacklist
- 빠른 조회가 필요한 인증 데이터
- 만료시간이 존재하는 임시 데이터

## 8. 이메일 인증 기술 선택과 발송 구현 분리

회원가입과 비밀번호 재설정에는 사용자 본인 확인이 필요했다.

휴대폰 인증은 비용과 외부 연동의 복잡성이 상대적으로 높아, 프로젝트 환경에서는 이메일 인증이 더 적합하다고 판단했다.

단순 SMTP뿐 아니라 다음 서비스도 비교했다.

- Mailgun
- SendGrid
- Amazon SES
- Postmark

운영 기능과 확장성을 고려해 Mailgun을 선택하고, 발송 기능은 인터페이스로 추상화했다.

```text
EmailSender
├── ConsoleEmailSender
└── MailgunEmailSender
```

개발 환경에서는 실제 메일을 보내지 않고 콘솔에 인증번호를 출력할 수 있으며, 운영 환경에서는 Mailgun 구현체를 사용할 수 있다.

인증 목적도 하나의 값으로 처리하지 않고 `purpose`로 분리했다.

```text
SIGNUP
PASSWORD_RESET
EMAIL_CHANGE
```

이메일 인증은 단순히 메시지를 전송하는 기능이 아니라  
**계정 생성과 변경을 보호하는 보안 흐름의 일부**로 설계했다.

## 9. AI 기능을 Port-Adapter 구조로 분리

Module 3에서는 서비스 차별화를 위해 다음 AI 기능을 설계했다.

- 이력서 AI 평가
- 채용공고 기반 추천
- 사용자 강점과 부족 역량 분석
- 추천 자격증 및 강의 제공

외부 AI API 호출을 Application Service 내부에 직접 구현하면 특정 모델이나 공급자에 강하게 의존하게 된다.

따라서 다음과 같이 Port-Adapter 구조로 분리했다.

```text
Application Service
→ AI Port Interface
→ Gemini/OpenAI Adapter 또는 Stub Adapter
→ AI 응답 정제
→ 결과 저장
```

이 구조를 사용하면 외부 AI 공급자가 변경되어도 Application Service는 Port만 사용하므로 수정 범위를 줄일 수 있다.

또한 프롬프트 생성 책임을 `PromptBuilder`로 분리해 서비스 로직이 프롬프트 문자열 구성까지 담당하지 않도록 했다.

### Stub Adapter를 사용한 이유

실제 AI API는 다음과 같은 특성이 있다.

- 호출 비용이 발생함
- 응답 내용이 매번 달라질 수 있음
- 네트워크 및 외부 서비스 상태에 영향을 받음
- 응답 시간이 일정하지 않음

따라서 테스트에서는 고정된 결과를 반환하는 Stub Adapter를 사용해 서비스 흐름을 안정적으로 검증했다.

Stub은 기능이 미완성이라는 의미가 아니라  
**비용, 외부 의존성, 응답 변동성을 테스트에서 분리하기 위한 설계 선택**이었다.

## 10. 오래 걸리는 AI 분석을 비동기로 분리

채용공고 분석과 추천은 외부 AI API를 호출하기 때문에 일반적인 DB 조회보다 처리 시간이 길 수 있다.

동기 방식으로 처리하면 사용자는 AI 분석이 끝날 때까지 요청을 계속 기다려야 하며, 타임아웃이 발생할 가능성도 있다.

따라서 요청 접수와 실제 분석을 분리했다.

```text
사용자 요청
→ 추천 요청 검증
→ PENDING 상태 저장
→ 요청 접수 응답 반환
→ Async Service에서 AI 분석
→ 결과 저장
→ COMPLETED 또는 FAILED 상태 변경
→ 사용자가 결과 조회
```

역할도 다음처럼 분리했다.

- `JobPostingRecommendationService`
  - 요청 검증
  - PENDING 데이터 저장
  - 접수 결과 반환

- `JobPostingRecommendationAsyncService`
  - 실제 AI 분석
  - 응답 정제
  - 분석 결과 저장
  - 상태 변경

Spring `@Async`는 프록시 기반으로 동작하기 때문에 같은 클래스 내부에서 직접 호출하면 비동기가 적용되지 않을 수 있다. 이를 피하기 위해 비동기 처리 클래스를 별도 Bean으로 분리했다.

이 구조는 AI 처리 시간을 줄이는 것이 아니라  
**오래 걸리는 작업을 사용자 요청 흐름에서 분리해 응답성과 안정성을 확보하는 방식**이다.

다만 DB 트랜잭션이 커밋되기 전에 비동기 작업이 시작될 가능성은 남아 있어, 이후에는 트랜잭션 커밋 이후 이벤트를 발행하는 방식으로 개선할 필요가 있다.

## 11. API 계약과 프론트엔드 협업

API 설계에서는 데이터의 위치도 중요한 계약이었다.

예를 들어 다음 API가 있다고 가정할 수 있다.

```http
POST /resumes/{resumeId}/ai-review
```

- `resumeId`
  - 평가 대상이 되는 핵심 리소스
  - Path Variable 사용

- `jobPostingId`
  - 비교 분석에 선택적으로 사용되는 값
  - Request Body 사용

Path에는 어떤 리소스를 대상으로 작업하는지 표현하고, Body에는 해당 작업을 수행하기 위한 추가 데이터를 전달하는 기준을 적용했다.

이 기준을 Swagger와 Notion 명세에 함께 정리해 프론트엔드가 요청 구조를 명확히 이해할 수 있도록 했다.

---

## 12. 데이터 정합성과 동시성 검토

DBA 역할에서 특히 중요하게 본 것은 데이터 정합성이었다.

다음과 같은 기능은 데이터가 한 번 잘못 저장되면 사용자 신뢰와 직접 연결된다.

- 결제
- 크레딧
- 수강 등록
- 중복 장바구니
- 추천 결과 상태
- 이메일 인증 상태

결제나 크레딧 처리에서는 단순히 처리 속도를 높이는 것보다 정확한 결과를 보장하는 것이 더 중요하다.

동시에 여러 요청이 잔액을 수정하면 다음 문제가 발생할 수 있다.

- 잔액 불일치
- 중복 차감
- 중복 결제
- 수강 데이터 중복 생성

따라서 충돌 가능성이 높고 반드시 순차 처리가 필요한 영역에서는 비관적 락을 사용할 수 있도록 기준을 검토했다.

**금액 처리에서는 빠른 처리보다 정확한 처리가 우선되어야 한다**는 것이 데이터 구조를 검토하며 세운 중요한 원칙이었다.

## 13. Flyway를 활용한 DB 변경 이력 관리

팀 프로젝트에서 DB 변경을 각자 수동으로 적용하면 팀원마다 스키마가 달라질 수 있다.

이를 방지하기 위해 Flyway migration 파일로 DB 변경 이력을 관리했다.

```text
V1__init_schema.sql
V2__init_data.sql
```

ERD가 변경되면 migration 파일에도 변경사항을 반영해 로컬, 테스트, 배포 환경에서 동일한 DB 구조를 재현할 수 있도록 했다.

Flyway를 사용하면서 DB도 애플리케이션 코드와 마찬가지로  
**변경 이력을 남기고 버전 관리해야 하는 대상**이라는 점을 배웠다.

## 14. 구현 구조를 설명 가능한 문서로 정리

Module 3에서는 코드 구현뿐 아니라 다음 내용을 팀원과 발표 평가자가 이해할 수 있도록 문서화했다.

- 전체 시스템 구조
- FE-BE 요청 흐름
- API 흐름
- 데이터 저장 흐름
- JWT 인증 흐름
- 클린 아키텍처 패키지 구성
- global 패키지
- Swagger 사용 방식
- 이메일 인증 기술 선택 근거
- AI 기능 설계와 비동기 처리
- 개인 발표 목차와 대본

팀 프로젝트에서는 코드가 동작하는 것만큼  
**왜 그렇게 설계했는지 다른 사람이 이해할 수 있도록 공유하는 일**도 중요했다.

문서화 과정에서 내가 이해하지 못한 구조는 설명할 수 없다는 점을 체감했고, 설명하기 위해 구조를 다시 검토하면서 기술에 대한 이해도 함께 깊어졌다.

## 아쉬웠던 점과 향후 개선 방향

Module 3는 전체 프로젝트의 초기 단계였기 때문에 모든 설계가 완성된 것은 아니었다.

다음 단계에서는 다음 항목을 개선할 필요가 있다.

### AI 비동기 처리 안정화

트랜잭션 커밋 이후에 비동기 작업이 시작되도록 이벤트 기반 구조를 적용할 수 있다.

### AI 전용 Executor 분리

기본 비동기 스레드풀 대신 AI 작업 전용 Executor를 구성해 동시 호출 수와 대기열을 관리할 수 있다.

### AI 응답 검증 강화

외부 모델의 응답을 바로 사용하지 않고 JSON 스키마 검증과 내부 데이터 매칭 과정을 강화할 수 있다.

### DB 마이그레이션 운영 규칙 구체화

팀원이 동시에 migration 파일을 추가할 때 버전 충돌이 발생하지 않도록 파일명과 담당 범위 규칙이 필요하다.

### 데이터 정합성 테스트 보강

결제, 크레딧, 수강처럼 중요한 도메인은 동시 요청을 포함한 통합 테스트를 더 강화할 필요가 있다.

## 배운 점

Module 3를 통해 백엔드 개발은 API를 구현하는 작업만으로 완성되지 않는다는 것을 배웠다.

기능이 정상적으로 작동하기 위해서는 다음 요소가 함께 고려되어야 한다.

- 데이터가 어떻게 연결되는가
- 각 도메인의 책임은 어디까지인가
- 요청이 어떤 계층을 거쳐 처리되는가
- 오류를 어떤 형식으로 전달하는가
- 사용자를 어떻게 인증하고 권한을 확인하는가
- 외부 서비스의 장애와 변경을 어떻게 분리하는가
- DB 변경을 팀 전체가 어떻게 동일하게 적용하는가
- 구현한 구조를 팀원에게 어떻게 설명하는가

특히 DBA 역할을 수행하면서  
**데이터 구조는 기능 구현이 끝난 뒤 만드는 결과물이 아니라, 기능이 올바르게 동작하기 위한 출발점**이라는 사실을 체감했다.
